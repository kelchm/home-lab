# Log schema and collector evaluation

Evaluated 2026-10-18; UniFi syslog added 2026-10-19. Scope: how Kubernetes container logs and UniFi syslog are shaped and collected for VictoriaLogs, so Grafana can browse them by service, severity and message without per-source query knowledge. The [logging runbook](../runbooks/logging.md) describes current operation; this record keeps the decisions and the evidence behind them.

## Conclusion

Adopt the OpenTelemetry log data model as the stored schema and collect with Fluent Bit, replacing vlagent. VictoriaLogs stays the backend: Grafana's Loki-only Logs Drilldown was considered and Loki rejected on efficiency, as in the original [bake-off](../observability-bakeoff.md).

The browsing problems traced back to inconsistent metadata rather than to the UI. A 7-day production inventory (117 sources, 6.39 million rows) found no stored service identity, no stored level on 47% of rows and seven level spellings among the rest, 42% of rows without a message (Traefik access logs), and 948 field names in one flat namespace where application keys such as `namespace` and `name` read like Kubernetes identity. vlagent records Kubernetes metadata and parses JSON and klog, but it cannot transform records, so none of this can be fixed in the current collector.

## Schema decisions

Each decision follows a published convention or an upstream implementation:

1. **Service identity.** `service.name` follows the OpenTelemetry Kubernetes rule ([semantic conventions v1.44.0](https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/docs/non-normative/k8s-attributes.md)): the `resource.opentelemetry.io/service.name` pod annotation, then the `app.kubernetes.io/instance` label, then `app.kubernetes.io/name`, then the owning workload, pod and container. The OpenTelemetry Operator and Grafana's Kubernetes chart (`alignServiceNameWithOTelSemConv`) use the same order. Pods whose labels give the wrong answer get the annotation.
2. **Missing levels.** Sources without a level store severity 0 (unspecified). The [data model](https://github.com/open-telemetry/opentelemetry-specification/blob/v1.61.0/specification/logs/data-model.md) lets UIs read that as INFO; storing INFO would invent information. A level the source states but the mapping cannot read is flagged with `pipeline.severity_unmapped`.
3. **Traefik message.** The body is Traefik's own `common` access-log line, which is what Traefik puts in the body when it exports OTLP itself ([v3.7.14 source](https://github.com/traefik/traefik/blob/v3.7.14/pkg/middlewares/accesslog/logger.go)). All fields stay as attributes.
4. **Request outcome.** Severity stays what the source logged. `http.response.status_code` is stored for every request and `error.type` only for 5xx responses, per the HTTP conventions' server rules; 4xx and client cancellations (499) are not errors.
5. **UniFi CEF.** Body from the event's `msg`, falling back to its name, as Elastic's CEF decoder does; CEF severity 0–3/4–6/7–8/9–10 to INFO/WARN/ERROR/FATAL, as Bindplane's OpenTelemetry collector does; parser-native `cef.*` names; `UNIFIutcTime` as the timestamp. No published CEF-to-OpenTelemetry mapping exists ([semantic-conventions #1460](https://github.com/open-telemetry/semantic-conventions/issues/1460) is open).
6. **Application fields.** Fields with a semantic-convention name use it unprefixed; all other application fields are prefixed by the application name, never by an existing convention namespace such as `app` ([naming guidance](https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/docs/general/naming.md)).

7. **Attribute shape.** Field names are schema, never data: arrays stay one value, an object whose keys are data is stored as one JSON string, and a record keyed that way stays in the message, as [VictoriaLogs' FAQ](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.53.0/docs/victorialogs/FAQ.md#how-many-fields-a-single-log-entry-may-contain) requires for dynamically keyed objects. A field moves to a semantic-convention name only when its source's documented format establishes the meaning, never by key name alone, so the Traefik mapping applies only to the `traefik` application; source locations are mapped only as `<file>.<source extension>:<line>`, and Traefik's `ClientAddr` is the connection peer because Traefik replaces `ClientHost` with the whole `X-Forwarded-For` value. Record time is the CRI timestamp: payload timestamps measured from whole seconds (Traefik) to nanoseconds, and promoting them would reorder lines. Deferred until a concrete need: promoting payload timestamps, HTTP fields of other applications, `exception.*` for `err`/`error`, logger names as instrumentation scope (this pipeline cannot set scope per record), and a shared convention for objects a controller reconciles. These rules were checked by a standards review, an edge-case review against a day of production fields and a necessity review.

Plain-text levels are read only at a fixed position in each format, never from words elsewhere in the line. That is established parser practice (Fluent Bit and Elastic parsers, the OpenTelemetry Collector's regex parser) and keeps the repository's rule against inferring severity from arbitrary text.

## UniFi syslog

Added October 19, 2026, when UniFi syslog moved from VictoriaLogs' built-in listener to Fluent Bit. A 10-minute packet capture of the export that day held 3,832 datagrams. The gateway's CEF lines carried no syslog priority. Every other line did: the gateway's daemon log at `daemon.info` with some `user.warning` and `user.err`, switches mostly at `daemon.debug` (DHCP snooping counters), and access points across `kern`, `user`, `daemon` and `authpriv` from `debug` to `crit`, including routine Wi-Fi driver messages at `kern.err`. Fourteen datagrams, all from one switch, carried a driver message and its continuation on two lines; VictoriaLogs had stored each continuation as a separate record without a header, about 190 a day.

The mapping follows from that capture:

- **Severity.** CEF events use decision 5. Other lines use the syslog severity as the [OpenTelemetry Collector's syslog parser](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.163.0/pkg/stanza/operator/parser/syslog/parser.go) maps it (`emerg` 21, `alert` 19, `crit` 18, `err` 17, `warning` 13, `notice` 10, `info` 9, `debug` 5) with the keyword as `severity_text`. A line with neither stays unspecified.
- **Identity.** `service.name` is the device name from the syslog header, because each device is what an operator browses; `service.namespace` is `unifi`. Host attributes follow the OpenTelemetry [host conventions](https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/docs/resource/host.md), which name switches as hosts: `host.name`, and for adopted devices `host.id` (MAC), `host.type` (model) and `os.version` (firmware) from the tag they send. Fluent Bit's OTLP output takes a chunk's resource from its first record ([v5.1.4 source](https://github.com/fluent/fluent-bit/blob/v5.1.4/plugins/out_opentelemetry/opentelemetry_logs.c)), so a stock `rewrite_tag` filter gives each device its own tag, by hostname or else sender address; without it, a local run labelled every device's records with the first sender's identity.
- **Message and time.** One datagram is one record, so the switch's two-line messages stay whole. CEF events take `UNIFIutcTime`; other lines keep their arrival time because RFC 3164 headers carry no timezone.

**Placement.** The existing DaemonSet receives syslog rather than a separate Deployment. With `externalTrafficPolicy: Local`, Cilium advertises the LoadBalancer address only from nodes with a Ready collector, so the sender's address survives for the network policy, each datagram reaches exactly one collector and a collector restart moves senders to the other nodes. Each collector buffers to its node's disk under the existing delivery guarantees. A single-replica Deployment would need its own buffer volume and would drop all UniFi syslog whenever it restarted; the withdrawn relay ([#867](https://github.com/kelchm/home-lab/pull/867)) showed the cost of a separate workload with its own queue and alerts.

**Cutover.** Each datagram goes to one Service backend, so the old and new paths never store the same datagram. The cutover takes two changes to avoid a gap. Flux applies `victoria-logs-single` before `fluent-bit`, so one change that deleted the old Service and created a new one would leave the address without a listener until the first Fluent Bit pod with the syslog port was Ready. Instead, Fluent Bit starts listening first, and the existing `victoria-logs-syslog` Service then changes its selector in place, so its backends switch from VictoriaLogs to Ready Fluent Bit pods in one update. The Service keeps its name and its place in the VictoriaLogs app, because renaming or moving it would recreate it.

**Verification.** `scripts/logging/test-fluent-bit.py` sends 14 UniFi datagrams from two sender addresses through the pinned image: CEF severities at each band boundary in use, header and extension escapes, the name fallback, an unmapped CEF severity, gateway, switch and access-point lines with their priorities and device tags, the two-line switch message, datagrams without a header from two senders and an out-of-range priority. Sent into VictoriaLogs v1.53.0, every UniFi record had a readable `_msg`, and the unchanged `UniFiWANFlapping`, `UniFiIntrusionDetectedOutbound` and `UniFiHoneypotTriggered` expressions matched their events and ignored internal and multicast detections.

## Talos node logs

Added October 19, 2026 ([#891](https://github.com/kelchm/home-lab/issues/891)). The mechanism and delivery facts come from the Talos v1.13.11 source: machined parses each service's line into `msg`, `talos-time`, `talos-level` and the line's JSON fields ([`extract.go`](https://github.com/siderolabs/talos/blob/v1.13.11/internal/app/machined/pkg/runtime/logging/extract.go)), sends one line at a time from each service's 1 MiB in-memory buffer, retrying a failed attempt (each up to five seconds) a second later and skipping a partly written line ([`circular.go`](https://github.com/siderolabs/talos/blob/v1.13.11/internal/app/machined/pkg/runtime/logging/circular.go), [`sender_jsonlines.go`](https://github.com/siderolabs/talos/blob/v1.13.11/internal/app/machined/pkg/runtime/logging/sender_jsonlines.go)), and reads the kernel log from the start of the ring buffer once the network is up ([`kmsg_log.go`](https://github.com/siderolabs/talos/blob/v1.13.11/internal/app/machined/pkg/controllers/runtime/kmsg_log.go)). Its kernel records carry no extra tags, so a receiver can only learn their node from where they arrive. The volumes come from `talosctl logs` and `talosctl dmesg` on all three nodes that day.

- **Placement.** The DaemonSet receives on a fixed ClusterIP with `internalTrafficPolicy: Local`, the established Talos pattern (a Fluent Bit `tcp` input behind a ClusterIP) narrowed to the node's own collector. On every node, Cilium 1.20.3 already resolves the one such Service, `hubble-peer`, to that node's backend only, and its socket load balancer serves host-namespace connections. Each record therefore reaches the collector that knows its node, without per-node Talos configuration. A central receiver behind a LoadBalancer, like UniFi's, would also catch a node's shutdown sequence after its pods stop, but would have to name each kernel record's node from its source address, an address-to-node table this design avoids, for a shutdown tail the node's console also shows. `hostNetwork` would take the collector out of Cilium policy.
- **Severity.** The level comes from where the source states it. Talos sets `talos-level` to `info` for every line without one and raises it to `warn` for any JSON `err` field, so it is used only for JSON lines from services that always state a level (containerd, cri, etcd); decision 2 leaves the rest unspecified. Their plain-text lines are read in their own formats: under 2% of `cri` lines came from CNI plugins (`[verbose]`), logrus text or klog, and `etcd` wrote klog and grpc-go lines. machined's controller logs put zap's level at a fixed position after the write time. Kubernetes JSON logs mark errors by omitting `v`. The kernel states a syslog priority, mapped as for UniFi.
- **Identity.** `service.name` is the Talos service or `kernel` and `service.namespace` is `talos`, with the node as `host.name` and `k8s.node.name`. Fluent Bit's OTLP output takes one resource per chunk, so a per-service resource would need a `rewrite_tag` emitter per service; in a local run, a burst across 17 services reached `storage.max_chunks_up`, the emitter paused the `tcp` input, and the paused input closed the connection ([v5.1.4 `tcp.c`](https://github.com/fluent/fluent-bit/blob/v5.1.4/plugins/in_tcp/tcp.c)), losing what Talos had written. `service.name` is sent as a record attribute instead; VictoriaLogs v1.53.0 decodes resource and record attributes into the same fields and picks the `VL-Stream-Fields` from all of them ([`pb.go`](https://github.com/VictoriaMetrics/VictoriaLogs/blob/v1.53.0/app/vlinsert/opentelemetry/pb.go)), so stored records are the same.
- **Time.** machined records the time it read a line, which is the delivery time for lines replayed from its buffer. Lines that begin with their writer's timestamp use it, as container records use the runtime's write time.
- **Volume.** Talos cannot select services. auditd (0.4–3.8 GB a day per node of SELinux AVC records), machined's successful authorization and API-call lines (87 MB a day per node, from the console dashboard), `dns-resolve-cache` debug lines (up to 34 MB) and the `kernel` service log, a text copy of what `KmsgLogConfig` sends structured, are dropped at the collector, leaving about 46,000 rows and 9 MB a day for the cluster.

**Verification.** `scripts/logging/test-fluent-bit.py` sends 30 Talos records over TCP through the pinned image: each drop rule and its kept counterpart, zap, Go-log, CNI, klog, logrus-text, grpc-go and JSON service lines, JSON messages that look like text formats, klog with trailing JSON, a logrus timestamp with an offset, kubelet info, error and nested records, three kernel priorities and an unrecognized record. A replay of node 1's captured buffers, 35,790 records sent at once, delivered all 25,055 expected records with no mapping errors. Sent into VictoriaLogs v1.53.0 with 30-day retention, every kept fixture was stored with `{k8s.node.name, service.name}` as its stream.

**Rollout.** Applied to the three nodes on October 21, 2026 ([#906](https://github.com/kelchm/home-lab/issues/906)). Each node's first delivery reached back to its October 5–6 boot with no output errors, retries, mapping errors or rows dropped by VictoriaLogs. k8s-prod-1 showed that `machine.logging.destinations` also sends Talos's `kernel` service log, a text copy of the `KmsgLogConfig` records, which the collector now drops. Restarting the collectors then left k8s-prod-1's kernel connection on the deleted pod for 16 minutes, losing 14 records.

## Kubernetes events

Added October 22, 2026, from [#746](https://github.com/kelchm/home-lab/issues/746). The API server keeps events for an hour, the kube-apiserver `--event-ttl` default that the Talos configuration leaves unchanged, and nothing stored them. A listing that day held 377 events, all `Normal`: 215 from kustomize-controller, and 113 with a `count` above 1.

- **Collector.** Fluent Bit's `kubernetes_events` input ([v5.1.4 source](https://github.com/fluent/fluent-bit/blob/v5.1.4/plugins/in_kubernetes_events/kubernetes_events.c)) lists events, then watches from the list's resource version, emitting `ADDED` and `MODIFIED` objects and ignoring `DELETED` and `BOOKMARK`. Each watch ends after `kube_watch_timeout` (10 minutes), and the input lists again, skipping objects at or below the highest resource version it has seen. It reuses the node collectors' image, chart and OTLP output. The OpenTelemetry Collector's events receivers would add a second collector, and `kubernetes-event-exporter`'s last release was in February 2024.
- **Placement.** One replica, replaced with `Recreate`. Every instance watches every event, so the DaemonSet would store each event once per node, and overlapping pods during a rollout would store them twice.
- **Repeated events.** The input's optional `DB` records each event once by uid, so later updates of a repeated event are dropped; with it, a test run lost a warning's next count. Without it, each count is a record, and a new process lists the last hour again, so a restart stores up to an hour of events twice. Repeats are routine (113 of 377) and restarts rare, so `DB` stays off.
- **Mapping.** As the OpenTelemetry Collector's Kubernetes events receiver ([v0.163.0 `k8s_event_to_logdata.go`](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.163.0/receiver/k8seventsreceiver/k8s_event_to_logdata.go)) does: the message as body; `Normal`, `Warning`, `Error` and `Critical` as severities 9, 13, 17 and 21, with the type as text; `k8s.event.*` and `k8s.object.*` attributes; the involved object's namespace as `k8s.namespace.name`; and the reporting host as `k8s.node.name`. There are three differences. The reporting controller falls back to `source.component`, which 2 of the 377 events set without `reportingComponent`. `k8s.event.start_time` keeps the API's RFC 3339 text. An unknown type is flagged with `pipeline.severity_unmapped`, as decision 2 does for logs.
- **Identity.** Every record's `service.name` is `kubernetes-events`, with `k8s.namespace.name` as the second stream field. The reporting controller as `service.name` could collide with an application's name in stream filters: kanidm's alert rules select `{k8s.namespace.name="identity", service.name="kanidm"}`, which would also match events reported under that name. Everything that varies per event is a record attribute, because the OTLP output takes a chunk's resource from its first record ([Talos node logs](#talos-node-logs)).
- **Time.** The input's own: `lastTimestamp`, else `firstTimestamp`, else `creationTimestamp`, so each count of a repeated event is stored at its occurrence. The receiver prefers `eventTime`, which only the 13 scheduler events set, in the same second as their `creationTimestamp`.

**Verification.** `scripts/logging/test-fluent-bit-events.py` runs the production configuration through the pinned image against a fixture API server that serves a list and a watch stream and then ends the watch, as the API server does at `timeoutSeconds`. Of 12 fixtures, the 8 kept records arrived with the expected fields: pod, node and CronJob events, a scheduler event with only `eventTime`, a reporter named only by `source.component`, an unknown type, a new warning and a repeated warning at counts 5 and 6. An expired event, a deletion, a bookmark and a stale resource version were dropped, and the second list stored nothing again. With `DB` set, the count-6 update was lost.

## Collector comparison

Measured locally on 2026-10-18 by replaying a one-hour production export (53,376 rows from 98 container files) at the production rate of about 12 lines/s, then a 2,000 lines/s burst. Memory is cgroup working set, the basis of the production vlagent figure. One collector processed all three nodes' files and no Kubernetes API was available, so per-node CPU in the cluster is lower.

| Collector | Memory steady / burst | CPU at 12 lines/s | Transformations |
| --- | --- | --- | --- |
| vlagent (production, per node) | 33–41 MiB | 3–4 mCPU | none |
| Fluent Bit 5.1.4 | 9 / 21 MiB | ~12 mCPU | Lua |
| OpenTelemetry Collector `otelcol-k8s` 0.163.1 | 66 / 72 MiB | ~85 mCPU | stock processors, OTTL |
| OpenTelemetry Collector contrib 0.163.1 | 92 / 101 MiB | ~85 mCPU | stock processors, OTTL |
| Grafana Alloy 1.20.1 (otelcol components) | 112 / 121 MiB | ~89 mCPU | stock processors, OTTL |

The OpenTelemetry Collector implements more of the mapping with stock components, but costs two to three times vlagent's memory and considerably more CPU, with beta log components and fortnightly releases. Fluent Bit was the lightest measured, ships a Kubernetes metadata filter with owner references, and buffers to disk. The mapping is about 300 lines of Lua and configuration under `kubernetes/apps/observability/fluent-bit/app/config/`.

vlagent's proposed transformation language ([VictoriaLogs #1508](https://github.com/VictoriaMetrics/VictoriaLogs/pull/1508)) expressed the same Kubernetes rules in a local trial with the maintainer's test image. It is unmerged, with changes requested and no release date. Revisit if it ships and keeping one VictoriaMetrics component matters more than Fluent Bit's lower footprint.

## Delivery

The September drills ([graceful outage](kubernetes-log-collectors.md); [SIGKILL during an outage](https://github.com/kelchm/home-lab/blob/26cb6da0d60e49733614246990ac1ae3567ca06d/docs/runbooks/logging.md)) were repeated against Fluent Bit 5.1.4 with a numbered fixture, kubelet-style rotation and filesystem buffering:

| Scenario | Fluent Bit | vlagent (September) |
| --- | --- | --- |
| 11-minute backend outage, graceful restart | 13,200/13,200, 0 duplicates | 12,839/12,839, 0 duplicates |
| SIGKILL, backend up | 2,400/2,400, 0 duplicates | not tested |
| SIGKILL during an outage | 33 missing, 0 duplicates; file rotated while stopped | 2,400/2,400, 529 duplicates |
| Buffer exhausted (deliberately tiny limit) | 2,336 missing; drop counter reported 1,072 | not tested |

The missing records in the third case were the unread end of a file that rotated while Fluent Bit was stopped. Including rotated files in the tail path recovers them but replays rotated files after every restart (2,700 duplicates after a graceful restart), and Fluent Bit's documentation says the path must not match rotated files. The configuration follows the documentation and accepts this compound case. Because the drop counter undercounts buffer-exhaustion loss, alerting fires on buffer capacity before exhaustion.

### Collector kills and power loss

Tested 2026-10-20 after the [multi-line evaluation](#multi-line-events) lost lines to SIGKILL at a higher rate ([#912](https://github.com/kelchm/home-lab/issues/912)). A local kind cluster (Kubernetes 1.37, containerd) ran Fluent Bit 5.1.4 from the production chart, values and configuration into VictoriaLogs v1.53.0, with the node's `/var/lib/fluent-bit` on a loopback XFS filesystem with the mount options of a Talos node's `/var`. The numbered fixture wrote 20,000 records at 250 per second, and its kubelet files held all 20,000. Production nodes averaged 2 to 4 container records per second on October 20, with peak minutes of 28 per second; a start-up replay reads far faster. `verify-numbered.py` checked every stored record's stream, severity, timestamp and body against what the fixture wrote. Each run killed the collector twice, away from the kubelet's 10 MiB rotations.

| Scenario | `storage.checksum On` | `storage.checksum Off` |
| --- | --- | --- |
| SIGKILL, six kills | 226, 43, 142, 182, 78, 119 lost | 0 lost |
| Simulated power loss (XFS shutdown), two runs | 35, 209 lost | 128, 47 lost |

No run duplicated a record or stored a damaged one. The tail input appends records to a chunk before it updates the file's position, so a kill between the two can still replay them as duplicates ([tail_file.c](https://github.com/fluent/fluent-bit/blob/v5.1.4/plugins/in_tail/tail_file.c)). With checksums on, the restarted collector rejected the chunks it had been writing as `invalid crc32` (logged at info level; `format check failed` at error). For the five kills whose rejected chunks were kept, two here and three in an earlier 36,000-line run, every lost record was in one of them, each chunk's content was intact, and its header held ChunkIO's running CRC: ChunkIO writes the unfinalized CRC into the header on every append and finalizes it only when it syncs the chunk, on lock, down or close ([cio_file.c](https://github.com/fluent/fluent-bit/blob/v5.1.4/lib/chunkio/src/cio_file.c)). So a kill between syncs always fails the check. The content length in the header is updated after each append is copied in, so without the check a killed chunk loads consistently, except during a new chunk's first copy, while the length is still 0: the loader then infers the length from the file size. Without `storage.delete_irrecoverable_chunks`, rejected chunks stay on disk and are checked again at every start. Fluent Bit's master branch has the same code, and [fluent-bit#10952](https://github.com/fluent/fluent-bit/issues/10952), with the same report, was closed as stale.

The power loss was simulated by shutting XFS down without a log flush during the run, then unmounting, recovering the log and restarting on the surviving state; it does not model a drive losing its write cache. In all four trials the chunk being written survived as an all-zero file, both settings rejected it for its header, and the lost records were its content, so the checksum made no difference. Tail positions (`DB.sync full`) were already on disk, but chunk data is synced only when the output takes the chunk, about once per flush interval.

Torn writes were tested by loading damaged copies of a real 174-record chunk with the production configuration:

| Damage | `On` | `Off` |
| --- | --- | --- |
| Header holds the running CRC (state after a kill) | rejected | 174 delivered |
| Content zeroed from the middle, one content page zeroed, or one page of random bytes | rejected | first 87 delivered, rest dropped without a log line |
| One page zeroed inside a 40 KB record | rejected | 173 delivered, and that record with its body cut to 2,059 characters |
| Length 0 and the first record cut off after 300 bytes (a kill during the first copy) | rejected | that record delivered without most of its resource attributes |
| Content length 0 in the header (header page from the chunk's creation) | rejected | 174 delivered (length inferred from the file) |
| File truncated inside the content, or header page zeroed | rejected | rejected |
| Tag metadata garbled | rejected | kept on disk, no route |

In every case the collector stayed up, delivered new records from another file and did not retry the damaged chunk. MessagePack decoding catches damage that breaks a record's structure, not zeros inside a string, so with checksums off a zeroed span can reach VictoriaLogs inside a record. ChunkIO only appends to a chunk's content, and unwritten XFS extents read as zeros, so torn chunks hold zeros rather than stale data.

**Decision.** Turn checksums off. With them on, a kill, including an OOM kill, discards every chunk written since its last sync, about a flush interval of each busy file's records, although the data is on disk and consistent. With them off, the kills lost nothing, the simulated power losses lost the same as with them on, and a damaged chunk delivers the records before the damage instead of none. The cost is integrity checking: a damaged chunk can deliver a record with a zeroed or missing span, and drops the records after damage that breaks decoding without a log line, where the checksum would have rejected the whole chunk with an error. Damage takes a power loss or a kill during the copy of a new chunk's first append; loss to the checksum comes with any kill while files are being read.

**Production check.** On 2026-10-21, with checksums off live, the runbook's kill drill ran on k8s-prod-3 (Talos 1.14.4, `/var/lib/fluent-bit` on the node's XFS `/var`). The numbered fixture wrote 20,000 records at 250 per second, and its kubelet files held all 20,000. The collector was killed twice with SIGKILL, 30 seconds apart and before the fixture's first rotation. VictoriaLogs stored all 20,000 records once each, every record passed the checks, and the restarted collector logged no warning or error.

Revisit if a Fluent Bit release keeps a valid CRC in the chunk header between syncs: checksums on would then lose nothing to a kill, and would reject a damaged chunk instead of delivering its records with a zeroed span.

## Multi-line events

Evaluated 2026-10-19 and 20: each container line stays one record, with no multi-line grouping at collection.

**Volume.** From 12:00 to 21:50 UTC on October 19, 2,327 of 359,740 container records (0.65%) were continuation lines with unspecified severity: indented lines, JSON brackets, `Traceback`, chained-exception headers, `goroutine` or `panic:`. mcphub's pretty-printed tool-call results made up 2,236 and four pve-exporter tracebacks 91. In the 30 days to that date production logged no Go runtime panic and no recovered `http: panic serving`; the only stored panic came from a scratch VictoriaLogs. mcphub v1.0.41 pretty-prints every logged object with a fixed two-space indent and has no log-level setting, so its dumps cannot be reduced by configuration.

**Test bed.** A local kind cluster (Kubernetes 1.37, containerd) ran Fluent Bit 5.1.4 from the production chart and values with the production configuration and Lua, sending to VictoriaLogs v1.53.0. Fake workloads produced real CRI files: a Python 3.13 app writing request lines to stdout every 5 ms while logging chained tracebacks to stderr with `logging.exception` and `traceback.print_exc`; a Go binary that panics and restarts, and one whose HTTP handler panics under `net/http`'s recovery; mcphub's colour-coded header and JSON format; and separate events that resemble continuations (indented status lines and lone `}` after a traceback, JSON lines, a 200 KB line). Each run lasted two minutes, and each event carried an ID for exact checks.

| Configuration | Result |
| --- | --- |
| Production | Baseline: every line its own record; nothing lost or duplicated. |
| `multiline.parser cri, python, go, mcphub` on the tail input | No grouping beyond `cri` (checked locally before the kind runs). |
| Multiline filter, stock `python, go` plus an mcphub rule | Unsafe. 14 stdout request lines were joined into stderr tracebacks and also stored again on their own; 323 records lost their stream; 32 lone `}` lines were joined into other events. The stock Python parser has no rule for Python 3.11+ caret lines (`~~~^^^`) or chained-exception headers. |
| Multiline filter, one custom parser grouped by `stream` | No lost, duplicated or cross-stream lines, and the look-alike separate events stayed separate. Whole in two runs (memory and filesystem emitter): every Go runtime panic (5 of 5), recovered HTTP panic (59 of 59) and mcphub dump (290 of 290, each valid JSON); 69 and 70 of 72 `logging.exception` chains; 59 and 58 of 73 `traceback.print_exc` events. A split event became two records. Each mcphub cycle (dump plus two single lines) fell from 20 records to 3, and each HTTP panic from 19 to 2. |

The splits came 9 µs to 14 ms after the previous line, so arrival delay does not explain them. They are consistent with Fluent Bit 5.1.4's flush timer, which force-flushes every pending group once per flush interval regardless of when its last line arrived (`cb_ml_flush_timer` in [src/multiline/flb_ml.c](https://github.com/fluent/fluent-bit/blob/v5.1.4/src/multiline/flb_ml.c)), so an event in progress at that tick is cut; this was not traced per event. A longer interval would cut fewer events, not none.

The custom parser was about 20 regex rules: Python rules extended for caret lines and chained exceptions, Fluent Bit's Go rules, and an mcphub rule that matches its ANSI colour codes, because the multiline filter must run before every other filter, including the colour stripping in `normalize.lua`. Fluent Bit's documentation says several multiline filters on the same tags loop, and its stock parsers set no `key_group`, so grouping by stream needs a custom parser.

**What grouping would not change.** Grouped Python tracebacks and Go panics still store severity 0. Python's `logging` and gunicorn put the level on a header line before the traceback, and the tested parsers leave that line separate; including it would take a rule per header format. The Go runtime states no level. Grouped mcphub dumps keep the header's INFO.

**Cost.** In buffered mode every container record, not only multi-line ones, passes through the filter's emitter input (298,696 read, 289,903 re-emitted after grouping), whose storage defaults to memory. In one measurement at 2,000 lines/s the collector used 85 mCPU and at most 19.4 MiB, against 81 mCPU and 12.7 MiB for production. Grouped records wait up to the filter's flush interval, 1 second in the test.

**Delivery.** Fluent Bit was killed with SIGKILL halfway through each run at about 250 lines/s, and the stored request lines were counted:

| Configuration | Lines lost per kill |
| --- | --- |
| Production (`storage.checksum On`) | 60, 82, 129 |
| Production with `storage.checksum Off` | 0, 0, 0, 0 |
| Custom parser, memory emitter | 139, 10, 133 |
| Custom parser, filesystem emitter | 19, 68, 14 |
| Custom parser, filesystem emitter, `storage.checksum Off` | 1, 2, 2 |

Lost lines are gaps in the request IDs below the highest stored one; the count cannot see a lost tail or damaged payloads, and the state path was ext4 on a Docker volume rather than a node's XFS. No run duplicated a line. With checksums on, the restarted collector rejected the chunks it had been writing (`[storage] format check failed`, which covers several validation failures), whether or not grouping was enabled; [fluent-bit#10952](https://github.com/fluent/fluent-bit/issues/10952) reports the same and was closed as stale; [Collector kills and power loss](#collector-kills-and-power-loss) traces the failing check and records the decision. With checksums off the production configuration showed no gaps, and grouping still lost the lines it held when the collector died. The earlier drill's lossless SIGKILL ran at 20 lines/s.

**Decision.** Keep one record per line. Grouping would make mcphub's dumps readable as one record, but it costs a bespoke parser that must track application formats, routes every record through an extra buffer, loses held lines when the collector dies, still cuts some events at its flush timer, and leaves tracebacks and panics without a severity. No Java workload runs in the lab, so the stock `java` parser was not tested. Read a multi-line event with **Show context** in Grafana, or by pod and time in VMUI. Revisit if a source's multi-line events must be one record, for an alert or because operators read them often; the stream-grouped custom parser is the configuration to start from, with a filesystem emitter.

## Rejected

- **Loki with Logs Drilldown:** the most complete Grafana browsing experience, rejected on efficiency. Its keyword severity heuristic also contradicts the no-inference rule.
- **loki-vl-proxy** (Loki API over VictoriaLogs): worked locally with Logs Drilldown 3.0.0 once service and level were stored, but is six months old with one maintainer, and its level filters read only stored fields.
- **Logchef:** no surrounding-context view or export for VictoriaLogs.
- **Unpoller's Loki output for UniFi events:** the event endpoints return 404 on Network 10.x, and v5.6.3 duplicates entries ([collector loop](https://github.com/unpoller/unpoller/blob/v5.6.3/pkg/inputunifi/collectevents.go)).
- **Vector:** its `kubernetes_logs` source is documented as best effort without acknowledgements. A central Vector behind vlagent duplicates batches whenever vlagent's request times out during a backend outage, and bounding Vector's retries turns those failures into batches vlagent drops unless an extra shim translates status codes.
