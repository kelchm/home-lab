# Broader Hugging Face cache landscape

Surveyed September 26, 2026. This expands the [NAS cache evaluation](hugging-face-nas-cache.md); it does not qualify additional software for deployment. The initial recommendation narrowed the field before adequately comparing community projects. A working HF endpoint, a durable NAS library, and a distributed download system are different ways to address repeat downloads and all belong in the discovery phase.

## Discovery and evidence

Discovery covered GitHub repository names/descriptions for Hugging Face mirrors, caches and proxies; primary documentation; release histories; and leads from the independent Opus research. Candidates were checked for server-side retention, client changes, local storage, maintenance and upgrade behavior. Download-only clients, hosted public relay sites and forks are identified explicitly rather than counted as independent cache servers.

Repository creation dates below come from the GitHub API and establish project age, not production readiness. Releases, concrete bug fixes and documented integrations are stronger evidence than stars. A project's own deployment guide is not an independent operator endorsement. Shpiel and MatrixHub have the local execution evidence described in the main evaluation; the other candidates below remain documentation/source assessments.

A single deployment record does not establish broad adoption.

## NAS download managers and retained libraries

These can run ingestion on Athena and preserve model files for NFS access or LAN staging. Their UI/API does not automatically replace huggingface.co for arbitrary clients: ingestion is explicitly requested, and consumers use the resulting files or cache tree.

| Project | Evidence and fit | Boundary |
|---|---|---|
| **[Bodaay HuggingFaceModelDownloader](https://github.com/bodaay/HuggingFaceModelDownloader)** | Apache-2.0; project created June 2023; v3.2.0 released June 13, 2026. Go binary and Docker images, download UI, optional basic auth, standard HF cache, revision/file selection, resume, verification and filesystem mirror push/pull. Stronger project history than most small mirror servers. | Standard-cache support and the expanded UI arrived in v3 in January 2026. Its “proxy support” is an outbound HTTP/SOCKS proxy; “mirror” means copying cache directories. Neither means a pull-through HF_ENDPOINT server. |
| **[HuggingHack](https://github.com/tyedalwaves/HuggingHack)** | NAS-oriented model browser/downloader, plain files, existing-folder indexing and uploads. Relevant to managing a retained library and locally produced artifacts. | Young project; no documented transparent HF mirror. Private UI features still need access-control tests. |
| **[HFDesk](https://github.com/bashrusakh/hfdesk)** | Standard HF cache or LM Studio-style folders, download UI, resume, NAS mirroring and optional basic auth; v1.2.2 released June 28, 2026. | Its README identifies it as a Bodaay fork. Useful alternative UI, not independent evidence of an older caching backend or an additional HF server. |
| **[blackbeardlabs/hf-downloader](https://github.com/blackbeardlabs/hf-downloader)** | June 2026 project; Node/Express, SQLite and aria2; resumable jobs and plain model directories. | Download manager rather than Hub mirror; short history and more runtime components than Bodaay. |

Bodaay's [v3.2.0 release](https://github.com/bodaay/HuggingFaceModelDownloader/releases/tag/v3.2.0) records SHA-256 verification, streamed mirror copies and concurrency fixes. An [operator report of repeated large-file downloads](https://github.com/bodaay/HuggingFaceModelDownloader/issues/75) received a concrete maintainer diagnosis and fix in April. This is useful maintenance evidence, not proof that every large transfer or migration is safe. Its v3 migration documentation preserves legacy files but recommends re-downloading for the new cache layout; importing the existing collection without WAN payload must therefore be independently established.

## Distribution systems with a different client contract

| Project | Evidence and fit | Cost to this LAN |
|---|---|---|
| **[ModelExpress](https://github.com/ai-dynamo/modelexpress)** | Apache-2.0; repository created May 2025; v0.6.0 released September 13, 2026. Model cache/distribution service with [documented NVIDIA Dynamo integration](https://docs.dynamo.nvidia.com/dynamo/knowledge-base/kubernetes/model-loading/model-caching). Supports HF-backed acquisition and transfer to workers. | gRPC/engine integration rather than a general HF_ENDPOINT replacement. Current [deployment docs](https://github.com/ai-dynamo/modelexpress/blob/main/docs/DEPLOYMENT.md) require Redis or Kubernetes metadata. Disable eviction for retention and explicitly configure transfer when clients cannot share the NAS filesystem; the documented fallback can otherwise download directly from HF. |
| **[Dragonfly](https://github.com/dragonflyoss/dragonfly)** | Established open-source P2P distribution project. Current [HF integration](https://d7y.io/docs/next/operations/integrations/hugging-face/) supports `dfget hf://...`, revisions, tokens and recursive repository downloads. | Dedicated client and scheduler/peer infrastructure; no general HF Hub frontend established. Useful if distribution across many machines becomes the problem; retain an authoritative NAS copy independently of evictable peer caches. Older requests-based integration examples should not be assumed compatible with current HTTPX clients. |
| **[HFMC](https://github.com/aisoft9/hfmc)** | Apache-2.0; created August 2024; v1.0.0 and last push February 22, 2025. Shares models among LAN nodes with resumable multi-source downloads. | Requires its own client workflow; little recent maintenance evidence. Public-source fallback does not establish strict NAS retention. |

ModelExpress and Dragonfly deserve consideration for Spark distribution even though they are not drop-in mirrors. The NAS constraint still applies: locating retained storage on Athena while running the cache service elsewhere would not satisfy the requested topology.

## Full Hubs and misleading search matches

[KohakuHub](https://github.com/KohakuBlueleaf/KohakuHub), [CSGHub](https://github.com/OpenCSGs/csghub) and [Shardline](https://github.com/STEXS-Technologies/shardline) belong in the broader artifact-hosting landscape. Hosting local models is distinct from retaining every upstream download. CSGHub has an all-in-one deployment, but its [repository synchronization documentation](https://opencsg.com/docs/en/csghub/101/function/reposync/reposync_intro) limits community-edition sync sources to OpenCSG and reserves custom remotes for enterprise; that is a concrete fit issue for a free HF cache. MatrixHub is already in the direct comparison because it implements proxy projects as well as hosted repositories. Nexus and Artifactory remain documented alternatives, without treating enterprise-platform history as the maturity target for this homelab.

Several search results do not add an independent NAS cache option:

- [padeoe/hf-mirror-site](https://github.com/padeoe/hf-mirror-site) publishes a Caddy-based mirror site. Its existence and popularity do not establish durable NAS byte retention.
- [light-hf-proxy](https://github.com/shiyemin/light-hf-proxy) is a Python client shim using relay/mirror services; its README explicitly does not provide the server implementation/setup.
- [aliendao](https://github.com/git-cloner/aliendao) provides download tooling for an external mirror, not an established local HF cache daemon.
- [Mirrors-Project/hf-mirror](https://github.com/Mirrors-Project/hf-mirror) is an Olah fork, not independent maturity evidence. Cloudflare Worker relays and inference-response caches likewise do not satisfy NAS-resident model storage merely by using “proxy” or “cache” in their names.

## Revised comparison priorities

Keep Shpiel as the measured baseline, not the selected winner. **MatrixHub's integrated mirror** now has a successful local UI and complete-snapshot reuse trial, but v0.2.0 fails cached reads during an upstream outage after metadata expiry; see the [measured results](hugging-face-nas-cache.md#matrixhub-local-trial-and-source-findings). Continue its bounded local evaluation in [#614](https://github.com/kelchm/home-lab/issues/614): offline serving is required before adoption, with a small maintainable fix acceptable. **Bodaay plus NAS staging** remains the fallback if that requires disproportionate work. Standalone hfd and ModelKeep remain relevant backend candidates, with ModelKeep's very short history accounted for. DingoSpeed is lower priority for this preference: it supplies a basic repository listing and management APIs, while its [design document](https://github.com/dingodb/dingospeed/blob/f2ae4376b4493ef72430cda0358c19401e0f94b1/docs/cache-admin-plan.md) places the management UI in a separate Spinfield application. No public repository or installation guide for that application was established. HugRS warrants consideration, but its known invalidation migration makes it a weaker fit for a sole retained copy.

Qualification must use the same contract: a complete pinned model reaches a second empty client with zero repeat WAN payload, survives restart/upgrade and unavailable upstream, resumes large transfers, imports existing data without re-downloading it, and keeps protected cached bytes protected. [Issue #608](https://github.com/kelchm/home-lab/issues/608) tracks the remaining comparison and NAS acceptance. Live tests remain Mac-only; no mirror is deployed on Athena.

## X operator research

On September 26, a separate Grok 4.6 pass searched X natively for posts dated **January 1, 2024–September 26, 2026**, beginning with workflows rather than candidate names. The exported session records 22 keyword searches, four semantic searches, 14 thread reads and five primary-source web fetches. Queries included HF caches with NFS/NAS/Synology/TrueNAS, Spark/GB10 cache sharing, HF_ENDPOINT, Xet failures, and Chinese-language mirror/cache terms. **Coverage: checked for shared-filesystem practice in a small sample; thin for a NAS-hosted UI plus transparent Hub mirror.** Counts describe search effort, not independent deployments.

These are firsthand experience reports found by Grok, not locally reproduced results. Direct X pages could not be independently opened through the ordinary web reader; primary project documentation was checked separately. Dates were cross-checked against post IDs. Two posts by the same operator count as one operator.

| Author and date (UTC) | Reported practice or problem | Evidence boundary |
|---|---|---|
| [Haydon Ryan, August 11, 2026](https://x.com/haydonryan/status/2087017706323169635) | Uses an NFS-mounted HF cache across vLLM machines; an earlier July post describes satisfaction with that approach. | One operator, not two independent reports. No locking, throughput or upgrade measurements. |
| [TechMD, August 3, 2026](https://x.com/TechMDAI/status/2084304369227293084) | Moved toward NFS model storage across Sparks after per-machine copies filled NVMe. | Spark storage pooling; does not establish that a dedicated NAS owns ingestion. |

| [sunny_gonna, September 21, 2026](https://x.com/sunny_gonna/status/2102082146836050037) | Reports several TB of models/datasets on NAS in the standard HF layout, asking whether a torrent overlay can reuse it. | Evidence of the existing NAS library; the overlay's compatibility remained unanswered. |
| [PlusTen, August 31, 2026](https://x.com/PlusTen_AI/status/2094366981474689109) | Reports a two-Spark recipe hardcoding the default cache path despite relocated HF_HOME; a maintainer reply claims a fix. | Supports checking the actual container mount/download stage. The patch and deployed fix were not independently verified. |
| [David Schaub, July 29, 2026](https://x.com/dsnein/status/2082272195682717787) | Reports out-of-memory behavior on PC and NAS with Xet high-performance and sequential-reconstruction settings. | One configuration-specific failure report, insufficient to reject Xet or network storage generally. |

This sample provides actual-use evidence for a shared filesystem library across inference hosts. It does not establish an overall community consensus, safe multi-writer operation, permanent offline retention, or a dependable combined UI/HTTP-mirror product. Named-project searches mostly added announcements or no relevant operator results. Missing X evidence is not proof that a project has no users.

Two leads were checked against their primary documentation:

- **[Oh My HuggingFace](https://github.com/fzlzjerry/ohmyhf)** has a model browser, resumable verified downloads and standard HF cache storage. It is an Electron desktop application distributed for macOS/Windows/Linux, not a packaged NAS web service. Its X discovery was a project repost rather than a NAS deployment report; it does not resolve the requested runtime location.
- **[hf-mount](https://github.com/huggingface/hf-mount)** is Hugging Face's lazy FUSE/NFS view of remote repos/buckets. Its documented cache defaults to roughly 10 GB under `/tmp`, and cross-node file locking is unsupported. It addresses remote filesystem access; this pass did not establish permanent NAS retention. Do not conflate its NFS backend with exporting an already retained HF library from Athena.

The useful addition beyond README comparisons is independent operator support for the shared-library architecture and a concrete cache-path integration failure. A NAS-owned downloader with controlled writes and read-only/staged consumers is still an engineering proposal, not a configuration proven by these posts. Use **HF_HUB_CACHE** for shared model storage; [HF_HOME also contains credentials](https://huggingface.co/docs/huggingface_hub/en/package_reference/environment_variables#hfhome). This corrects the researcher's suggestion to share HF_HOME wholesale. Broad advice in the raw report to treat Ceph-like filesystems as hostile is also not adopted from isolated X reports.
