# Grafana VictoriaLogs datasource v0.33.1 qualification

## Decision and scope

On October 22, 2026, Grafana Explore replaced Kubernetes / Logs as the routine entry point and the dashboard was removed; the logging runbook's [Query logs](../runbooks/logging.md#query-logs) describes the current workflow. The qualification record below is unchanged.

**Recommendation: adopt with the limitations below; retain Kubernetes / Logs as the routine entry point.** The candidate adds useful field/stream discovery and patterns, but the trial does not establish a substantial improvement to a scoped application-incident workflow. The operator found the Fields view noisy. It mixes infrastructure labels, IDs and application internals without a preferred-field or hide-list configuration. Normalized service and severity exist in the dashboard query, which the drawer discards. A plugin upgrade alone does not provide a curated log explorer.

Qualification began on October 18, 2026, with both `main` and production using datasource v0.31.0, Grafana `13.2.4-distroless` and VictoriaLogs `v1.53.0`. The upgrade in [#868](https://github.com/kelchm/home-lab/pull/868) changed only the logs-plugin URL pin; Grafana, its chart, other plugins, dashboards, datasource configuration and ingestion were unchanged by that PR. Subsequent production verification is recorded below. No existing issue/PR covered this upgrade; #740 retains its separate login/backup acceptance, and #856 belongs to the parallel syslog work.

### Counts, limits and loading

Ordinary Explore logs retain the provisioned 1,000-line default, with a 10,000 hard cap. Volume uses a separate hits query with no log-line limit. The drawer's details Logs sample is capped at 100 and an expanded breakdown sample at 50. A count badge is not the number of visible sample rows.

The main patterns list uses `sample 10`, multiplies sampled hits by ten, and retains at most 100 patterns. Rare patterns can be absent. Percentages are relative to loaded breakdown rows, not necessarily the whole dataset. Filtering a pattern uses an unsampled pattern predicate; use an explicitly bounded stats query for an incident total. [Tagged query construction](https://github.com/VictoriaMetrics/victorialogs-datasource/blob/v0.33.1/src/components/QueryEditor/Drilldown/queries/drilldownQueries.ts) and [breakdown presentation](https://github.com/VictoriaMetrics/victorialogs-datasource/blob/v0.33.1/src/components/QueryEditor/Drilldown/shared/BreakdownTable.tsx) establish these limits.

Calendar-aligned edge buckets need care. The fixed-window API trial's hits sums were 63/260/6,677 against stats counts 63/258/6,641. A separate exact `_time:[start,end)` namespace query gave matching hits/stats totals of 7,219. This supports using an explicit time predicate for exact totals; it does not establish that a chart legend's sum equals the selected-window row count. [The hits API](https://docs.victoriametrics.com/victorialogs/querying/#querying-hits-stats) aligns bucket timestamps, which can precede the selected start, and Grafana's visible edge buckets also affect presentation.

Incremental loading applies to Explore Raw Logs, not the drawer. It first requests logs, then volume. The three-second budget concerns response headers, not total body completion. Slow requests trigger newest-to-oldest histogram bars. Pause waits for the active bar; Stop keeps completed bars and can release a deferred log request; Explore Cancel cancels the active requests; already-rendered log results can remain visible. Group hits by keeps up to 20 groups per bar with the tail in `other`, so that tail can differ from a whole-range grouping. Partial or stopped volume is not a full-window count. See [upstream behavior](https://docs.victoriametrics.com/victorialogs/integrations/grafana/#incremental-hits-loading).

## Operator experience and follow-on options

The established service-first approach is a small consistent stored identity plus message/severity fields, with raw metadata available on demand. [OpenTelemetry service conventions](https://opentelemetry.io/docs/specs/semconv/resource/service/) and the [logs data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/) provide a reference contract; adopting their field names does not require replacing this backend. The candidate already recognizes `service.name`, `service_name`, `service` and `app` for its initial breakdown. The current dashboard derives service and several severity formats at query time, so its aliases do not improve a fresh `*` drawer. Storing those aliases could improve discovery, but would not remove Fields clutter or fix handoff scope/time.

A useful UI follow-on would support preferred/hidden fields, preserve the incoming expression and filters, and transfer time explicitly. None is supplied by this pin. Grafana's separate [Logs Drilldown](https://grafana.com/docs/plugins/grafana-lokiexplore-app/latest/) is built for Loki, so it is not a drop-in interface for VictoriaLogs. [Logchef](https://docs.victoriametrics.com/victorialogs/integrations/logchef/) is an upstream-documented alternative for the existing backend; it was not trialed here. Backend replacement, schema changes and a new dashboard remain outside this PR.

[#871](https://github.com/kelchm/home-lab/issues/871) tracks the bounded comparison of supported Grafana field curation and handoffs, a minimal stored service/severity contract, and a read-only Logchef trial if the Grafana path remains insufficient. No follow-on implementation or alternative-UI trial was performed during plugin qualification.

## Acceptance and rollback

The operator accepted the candidate with its documented limitations on October 18, 2026, after the walkthrough and discussion of noisy Fields. Keep Kubernetes / Logs as the routine entry point and verify scope/time when handing off from the discovery drawer. This is acceptance of the qualified plugin upgrade, not evidence of a substantial improvement to scoped incident investigation. Production login/backup acceptance remains with its existing work; this plugin trial does not close it.

PR #868 merged at 19:10 UTC on October 18. Flux reported the Grafana Helm upgrade successful at 19:10:42 UTC. Read-only production API checks at 19:33 UTC confirmed datasource plugin v0.33.1 with `signature=valid` and datasource health `OK` (`Data source is working`); Grafana was 3/3 Ready. These checks establish installed version and backend connectivity, not a repeat of the browser qualification or OIDC/backup acceptance.

The remaining scratch `grafana-vl-trial` pod, its two ConfigMaps and its trial-only network policy were deleted at 19:33 UTC, and their absence was verified. The localhost:3301 port-forward and delayed cleanup process were stopped. The separate retained-storage test instance had already been retired. Production resources were not changed during cleanup.

Production rollback is a reviewed revert of the complete plugin URL/version pin to v0.31.0, followed by the separately authorized Flux rollout. Keep the original Grafana PVC, datasource UID and dashboards. Verify the installed version/signature and datasource health after restart; a changed Helm value alone does not prove that a persisted plugin directory changed version. Expect the existing single-replica Grafana restart gap. The scratch retained-storage trial above verified both upgrade and rollback through the same synchronous installer setting used in production. Local checks also passed `flate test all --path kubernetes/flux/cluster --no-progress` (168 resources), dashboard generation consistency, the docs index and `git diff --check`. Grok's independent review is recorded in #868. The initial Claude attempt was rate-limited; a resumed Claude Opus 5.5 review completed after merge, found no blockers, and corroborated the source/API artifacts and production version/health without repeating browser acceptance.
