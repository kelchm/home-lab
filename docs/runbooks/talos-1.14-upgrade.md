# Talos 1.14 upgrade

This procedure covers the k8s-prod v1.13.11 → v1.14.4 OS upgrade and the live Cilium SELinux acceptance check tracked in [#921](https://github.com/kelchm/home-lab/issues/921) and [#911](https://github.com/kelchm/home-lab/issues/911). The approved OS rollout ran on October 20, 2026 (October 21 UTC), in node order 2 → 1 → 3. All three nodes now run Talos v1.14.4 with Kubernetes v1.36.4. Read-only host-label checks confirmed `pod_containerd_run_t` on `/run/cilium` and `/run/cilium/state` on every node; timed audit evidence and the remaining sources are recorded in [#911](https://github.com/kelchm/home-lab/issues/911).

## Compatibility and configuration

The [v1.14 support matrix](https://docs.siderolabs.com/talos/v1.14/getting-started/support-matrix) includes Kubernetes 1.36. [Talos v1.14.4](https://github.com/siderolabs/talos/releases/tag/v1.14.4), released October 16, is the latest stable v1.14 patch checked during preparation. It uses Linux 6.18.57, containerd 2.3.7 and default etcd 3.7.2. Kubernetes stays pinned to v1.36.4; an OS upgrade does not upgrade Kubernetes.

Read the [v1.14.0 release notes](https://github.com/siderolabs/talos/releases/tag/v1.14.0), the intervening patch release notes, and the [upgrade guide](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/lifecycle-management/upgrading-talos) before operating:

- Existing v1alpha1 machine configuration remains supported. Freshly generated 1.14 configuration moves DNS, discovery, encryption and control-plane settings into separate documents. The repository's resolver and controller patches use those documents so regeneration succeeds. The API certificate SANs are explicitly preserved because talhelper 3.1.17 does not transfer `additionalApiServerCertSans` into `KubeAPIServerConfig`.
- New-cluster workload isolation is opt-in for an upgraded cluster. The generated configuration contains no `SecurityProfileConfig`, so this rollout does not enable sandboxd isolation. The compatibility patch removes the generator's new weekly `FilesystemTrimConfig` to keep trim disabled as it is today. CI rejects either document in this rollout's render.
- A future configuration apply introduces the document-path kube-apiserver authentication file and startup probes. Its generated anonymous authentication is restricted to `/livez`, `/readyz` and `/healthz`, so anonymous `/version` and discovery requests can change to 401. The retained legacy configuration does not opt into this behavior on the OS upgrade alone. Treat this as a separately approved configuration migration: review anonymous clients and verify API probes and existing authenticated clients after applying.
- Talos 1.14's OOM controller defaults to strict cgroup QoS class ordering even without an `OOMConfig` document. This OS-level change can affect victim selection under memory pressure. Check and record any OOM actions on the canary alongside workload placement; they are separate from the AVC signal.
- Talos raises the minimum TLS version for etcd and kube-apiserver to TLS 1.3. The etcd HTTP endpoint moves from 2379 to 2383, but this repository explicitly sets `listen-metrics-urls: http://0.0.0.0:2381`; its metrics listener remains on 2381. The new 2383 listener still needs to be considered in any host/network firewall policy.
- The multipath-tools configuration migration does not apply: that extension is absent. Longhorn uses CSI, so removal of the old FlexVolume path and the in-tree iSCSI isolation limitation do not apply to its volumes. Secure Boot is disabled on these nodes.
- The target factory catalog contains all five schematic extensions: `amd-ucode`, `amdgpu`, `iscsi-tools`, `realtek-firmware`, and `util-linux-tools`. Keep the existing schematic `7c9e329e408b058e4bdb5e18e4af75eed95d5b53944d6024fa59f8fa235e1741`. Its existing `factory.talos.dev/installer/<id>` URL and the documented `metal-installer/<id>` URL resolved to the same v1.14.4 OCI index during preparation.
- Deployed Cilium is v1.20.3. Its [Kubernetes requirements](https://docs.cilium.io/en/v1.20/network/kubernetes/requirements/) include 1.36, and Linux 6.18 exceeds its minimum kernel requirements. Preserve the current Cilium/Multus configuration and verify datapath recovery after each reboot.
- Deployed Longhorn is v1.12.1. Its [Talos requirements](https://longhorn.io/docs/1.12.1/advanced-resources/os-distro-specific/talos-linux-support/) require the existing `iscsi-tools` and `util-linux-tools` extensions and privileged admission. Existing data paths and shared mounts are retained. No vendor matrix certifies this exact Longhorn/Talos patch pair; the storage gates remain the live acceptance test.
- Deployed Multus is v4.3.1-thick, whose [release](https://github.com/k8snetworkplumbingwg/multus-cni/releases/tag/v4.3.1) includes Kubernetes 1.36.2 dependencies. Preserve the existing netns mount, private Cilium source directory, fail-closed CNI publishing, whereabouts and untaint safeguards. The [Talos Multus guide](https://docs.siderolabs.com/kubernetes-guides/cni/multus) documents the relevant host-path behavior. There is no exact Talos patch compatibility matrix.

Talos stopped publishing `ghcr.io/siderolabs/installer` in 1.14, which explains the absent Renovate update; no repository version cap blocked it. `talenv.yaml` now tracks `siderolabs/talos` GitHub releases. Installer images still come from the schematic in Image Factory. The talosctl pin is already 1.14.4. Talhelper 3.1.17 is the [final archived release](https://github.com/budimanjojo/talhelper/releases/tag/v3.1.17), with 1.14 alpha machinery; keep its existing pin and validate generated output with stable talosctl 1.14.4. Its version warning and the remaining `.machine.files` deprecation do not replace validation. A renderer replacement is separate maintenance work.

## Regeneration and dry-run sequencing

Generate production configuration into a private temporary output directory, keeping the credential symlink intact. Generated node files and talosconfig contain credentials and must remain gitignored/local. Publish only redacted configuration and diffs. The [PR description](https://github.com/kelchm/home-lab/pull/922) contains expandable sections with redacted regenerated files for all nodes, the offline rendering diff, and native dry-run output.

After any direct `talhelper genconfig` invocation, run `scripts/talos/preserve-encryption.sh <output-dir>/*.yaml` before validating or considering the output for use. `task talos:generate-config`, the bootstrap task (through that same generation task), and CI run this automatically. Talhelper's new-cluster output calls the secretbox key `key1` and omits the identity fallback; this existing cluster uses secretbox `key2` followed by identity. The helper preserves the generated key material, changes the provider metadata to match the existing cluster, and refuses unknown provider layouts or a missing control-plane encryption document. CI checks provider names/order, unchanged fixture key material, required API SANs and all component image pins. Never apply an uncorrected direct talhelper render.

During preparation, all three 1.13 nodes rejected a full 1.14 dry-run with `DiscoveryServiceConfig` unregistered. This is a format-version boundary, not a successful apply preview. Repeat the full dry-run after each node runs 1.14, with a matching talosctl, before contemplating any configuration apply. Do not apply the new documents to a 1.13 node.

The OS upgrade retains the live configuration. Do not run `task talos:apply-node` as part of this OS-only acceptance test. An eventual configuration migration needs its own explicit approval and review of the post-upgrade dry-run. Talos 1.14 also removes apply-config's `--mode=reboot`; configuration changes requiring a reboot must be handled with the guarded node procedure.

A separate native dry-run using each node's exact persisted 1.13 config with only the installer tag changed succeeded on all three nodes and showed only that tag delta. This is an installer-only preview in the retained schema, not a successful preview of the full 1.14 render. Neither configuration was applied.

## Before the first node

Follow [the rollout skill](../../.agents/skills/talos-rollout/SKILL.md). The user merges the PR and approves each node separately in the conversation. Update the checkout to merged main and compare `talenv.yaml`, `.mise.toml`, and `talconfig.yaml` before running a task.

Check that `kubeconfig`, `talos/clusterconfig/talosconfig`, and `age.key` are usable symlinks to the main checkout; do not let talosctl create an empty config. Use explicit `--kubeconfig` for kubectl. For direct Talos queries use the node's running version, explicit talosconfig, endpoint and node:

```sh
mise exec 'aqua:siderolabs/talos@1.13.11' -- talosctl \
  --talosconfig "$PWD/talos/clusterconfig/talosconfig" \
  -e 10.32.30.12 -n 10.32.30.12 version
```

Preparation preflight found direct `en0` routes to the API and all three nodes, healthy etcd, three Ready/uncordoned nodes, 24 attached/healthy Longhorn volumes, three Ready instance-managers with `lhnet1`, and no suspended Flux Kustomizations. Both singleton database primaries were on node 3 (`visionect-db` and `bambuddy-db`). These observations expire: rerun preflight immediately before every approved node. Node 2 was selected as the first canary because it had neither primary and its audit baseline was mostly Cilium.

Before the first upgrade, save and verify an etcd snapshot outside the repository. Keep out-of-band power control available. Before node 3, explicitly settle both singleton database availability decisions using the skill's CNPG procedure and fresh placement/backup facts. Resolve eviction blockers deliberately; never force a drain or bypass Longhorn's policy. Any temporary topology or Flux suspension requires separate authorization, recording and deliberate restoration.

## Per-node procedure and AVC acceptance

Run only the approved node through `task talos:upgrade-node IP=<ip>`. Preflight selects a client independently for every node's version and etcd member query; its cluster health RPC uses the client matching the node serving that RPC. The task also runs the candidate's generated upgrade command inside `with-node-client.sh`. This helper reads that node's Kubernetes-reported OS with an explicit kubeconfig and selects the exact Talos version through mise. Missing credentials, a failed lookup or an unrecognized version aborts the command. It is intended for the healthy pre-upgrade state; after reboot use the expected 1.14.4 client and verify the server version before continuing. Preserve `--drain-timeout=15m`, `--timeout=20m`, and `--reboot-mode=powercycle`. Direct read-only Talos checks must also select the version matching each target node.

After the node returns, use talosctl 1.14.4 for it. Verify the version and the skill's complete gates: etcd quorum, every Kubernetes node Ready and uncordoned, every in-use Longhorn volume attached and healthy with none degraded/faulted, and every instance-manager Running/Ready with `longhorn-system/storage-network` on `lhnet1` and a `10.32.25.x` address. Verify Cilium, Multus and the untaint safeguards recover. Stop on any failure.

[Upstream #14046](https://github.com/siderolabs/talos/pull/14046) grants pods rw on `bpf_t` and changes directories created by `pod_p` under `run_t` to `pod_containerd_run_t`. The expected outcome is that kubelet recreates `/run/cilium` with the new label after reboot, and `state` and endpoint directories inherit it. Live read-only checks after this rollout confirmed both directory labels on all three nodes. The original `run_t`/`bpf_t` acceptance target is narrower than every Cilium AVC: low-rate `prog_run` denials against `sys_containerd_t` and `pod_containerd_t` appeared in the post-upgrade samples. These are BPF program operations, not filesystem `bpf_t` denials.

For each upgraded node:

1. Capture `talosctl logs auditd` and `talosctl dmesg` before and after approximately ten minutes, and continuously capture auditd with `talosctl logs auditd --follow` throughout the timed interval. Keep the raw logs private/local. Record the last audit serial, query timestamps, last printed `audit_lost`, node version and uptime; detect resets before computing deltas. Record the stream's start/end times and any disconnect, and filter records by audit timestamp to exclude the initial historical buffer. A snapshot-only or interrupted capture cannot establish zero AVCs over the interval; repeat the continuous capture before accepting that result.
2. Compute audit serial growth per second and last-printed `audit_lost` growth per second independently. They count different units (events versus records); do not subtract them. A quiet loss counter means no additional loss was reported during the interval, not a complete kernel audit-status query.
3. Count AVCs by `comm` and `tcontext`, decoding hex-encoded process names and distinguishing rotating-buffer samples from the continuous interval capture. Require no `cilium-agent` AVCs against `run_t` or `bpf_t` in the uninterrupted interval capture. Record other Cilium contexts if any appear. Increased `audit_lost` makes a zero count inconclusive because kernel-dropped records cannot reach the stream; record that limitation and corroborate with read-only label/policy evidence or repeat during a loss-free interval.
4. If an existing container has suitable read-only tools, inspect the SELinux labels on the host-mounted `/run/cilium` and `/run/cilium/state` (for example `ls -Zd`). Do not create a debug pod, relabel paths or install tools solely for this check without approval. If unavailable, record that limitation separately from the AVC result.
5. Record rates, sample/interval counts, label evidence, remaining sources and the health result in #911, then stop for the next node's approval.

Expect Longhorn-backed workloads to retain `unlabeled_t` denials and Multus to retain some `cni_state_t` denials. Workload movement may move the high audit/loss rate between nodes, so record placement alongside rates. Keep #911 open on `hold` until its Longhorn acceptance check and auditd collection decision are complete. Do not change #905 or #907.


## Verified rollout state

The operator merged [#922](https://github.com/kelchm/home-lab/pull/922) and approved each node individually. All three guarded upgrades completed with powercycle reboots, without a forced drain or physical power intervention. Storage returned fully healthy after each node; the post-reboot watchers took 2m01s for node 2, 4m49s for node 1 and 5m35s for node 3. An etcd snapshot outside the repository was checksum-verified and passed a local-only, hash-validating `etcdutl` restore before the first upgrade. The checksum was rechecked after the rollout. No Talos machine configuration was applied.

Before node 3, both CloudNativePG singletons received temporary streaming standbys and verified zero-lag switchovers using the client matched to CNPG 1.30.1. After the reboot, Bambuddy switched to its synchronized instance on node 2 to separate the primaries. The original complete Cluster specs are restored, each database has one Ready instance, and the RW services point to writable `visionect-db-2` on node 1 and `bambuddy-db-2` on node 2. CNPG reclaimed the surplus standby PVCs, PVs and Longhorn volumes; no replication slots remain. Both owning Kustomizations resumed and reconciled successfully.

The authorized rebalance placed VictoriaMetrics on node 3 and left VictoriaLogs on node 2. Longhorn has 24 attached, healthy volumes and 50 active replicas spread 16 / 17 / 17 across nodes 1 / 2 / 3. Replica moves ran one volume at a time, retaining at least two healthy RW copies throughout. Every temporary per-volume locality, replica-count and auto-balance setting was restored. The two database volumes have three replicas each; the other 22 volumes have two each. These are observed placements, not permanent scheduling constraints.

Older unreferenced replica directories were found separately from the active volume inventory. Their retention and any irreversible cleanup are tracked in [#925](https://github.com/kelchm/home-lab/issues/925); healthy volume status alone does not establish that historical recovery data should be deleted.


The simultaneous final audit captures ran for about 600.8 seconds on each node, from 04:04:10 to 04:14:11 UTC on October 21. The fresh pre-upgrade baseline ran for about 601.5 seconds per node. Workload movement matters: the final VictoriaLogs host is node 2 and the VictoriaMetrics host is node 3.

The remaining final AVCs were dominated by VictoriaLogs (`victoria-logs-p`, 10,375 received AVCs) on node 2 and VictoriaMetrics (`victoria-metric`, 2,798) on node 3, both targeting `unlabeled_t`. These counts describe received AVC records; they are incomplete on the lossy node. Zero reported loss growth uses the last printed dmesg `audit_lost` counter and is not a direct kernel audit-status query. [#911](https://github.com/kelchm/home-lab/issues/911) remains open on `hold` for Longhorn labeling acceptance and the auditd collection decision.

No new container restarts or kernel OOM messages were found. Repeated HTTP checks passed for VictoriaMetrics, VictoriaLogs, Grafana, Broadsheet, Visionect, Bambuddy and Kanidm, and all 136 scrape targets were up. All 25 HTTP routes were accepted and all seven certificates were Ready. Periodic queries confirmed all three etcd members responding and Talos health passing; the final complete rollout preflight also passed.
