# Kubernetes logging

All Kubernetes container stdout/stderr is stored in VictoriaLogs, which is the only log backend. **Production remains on Alloy until the separately approved per-node rollout below.** The repository stages vlagent alongside Alloy without selecting any nodes by default; merging the implementation does not authorize the cutover. [#583](https://github.com/kelchm/home-lab/issues/583) stays open through rollout, alert-delivery verification and cleanup.

## Query logs

- **Grafana Explore:** `https://grafana.home.kelch.io/explore` — select the `VictoriaLogs` datasource. This is the normal single-pane entry point. The query editor's `Run in VMUI` action carries the current query and time range to the external VMUI, and `View as JSON` is useful when the complete structured row is more useful than the selected `_msg`.
- **VictoriaLogs VMUI:** `https://vlogs.home.kelch.io/select/vmui/` — use the native LogsQL explorer and live-stream view. The bare hostname redirects here.

Grafana authenticates through its native `auth.generic_oauth` integration and dedicated Kanidm client; VictoriaLogs VMUI uses the OIDC middleware on its HTTPRoute. Useful LogsQL starting points are `namespace:observability`, `service_name:grafana`, `level:in("error", "critical")`, `stream:stderr`, and `namespace:observability | stats by (service_name) count()`. The time picker supplies the query window. These raw metadata filters select Alloy rows; during migration, use the dual-schema namespace selector and compatibility pipe described under [Query compatibility](#query-compatibility) to include vlagent rows.

## Alloy field model (retained history)

Current rows use `cluster`, `namespace`, `service_name`, `pod`, `container`, and `node` as their stream identity. Alloy derives `service_name` from `app.kubernetes.io/name`, then legacy `app`, then the container name. `app_instance` preserves `app.kubernetes.io/instance` when present, but remains an ordinary field because it normally identifies an application or Helm release rather than a unique OpenTelemetry service instance.

Alloy normalizes explicit JSON or credible logfmt severity aliases to the Grafana-native top-level `level` values `trace`, `debug`, `info`, `warning`, `error`, and `critical`; fatal and panic aliases fold into `critical` while the original payload remains intact. `level` is an ordinary VictoriaLogs field rather than part of stream identity. Grafana also has bounded compatibility rules for retained rows whose pre-normalization severity exists only in `msg.level`; no general message-text inference is used.

Structured application fields are stored below `msg.*`, preventing payload keys such as `namespace` from replacing Kubernetes metadata. VictoriaLogs derives `_msg` from `message`, `msg`, `log`, `event`, or `record.message` after applying that prefix; non-JSON lines remain unchanged in `_msg`. Alloy strips ANSI terminal color escapes after reconstructing CRI partial records so stored messages remain readable and searchable.

Use ordinary field filters for `app_instance`, `level`, `filename`, and `stream`. For example, `stream:stderr` works across both pre-hardening and current data, while a stream selector such as `{stream="stderr"}` matches only older rows where `stream` was part of `_stream`.

Grafana and all three Traefik instances emit their supported JSON console/access-log formats. Other applications keep their native output until a measured source-specific change is justified. Do not add a global multiline rule: CRI partial records are already reconstructed, and legitimate separator output can resemble continuation lines. Likewise, do not infer stored severity from arbitrary words such as `error` or `info`; an honest unknown level is safer than a false classification.

Retention is nominally 30 days, but VictoriaLogs begins deleting the oldest partitions at 80% disk use. The effective retention is whichever limit is reached first.

## Pipeline failures

Metrics-native rules page through VMAlertmanager when an Alloy target disappears, a node stops sending entries, retries persist, either layer drops data, VictoriaLogs becomes read-only or nearly fills its PVC, ingestion goes silent, or stream creation exceeds the measured rollout envelope. These alerts deliberately depend on the metrics path rather than querying the log backend they diagnose.

If an alert fires, inspect the affected Alloy component graph and writer metrics, the `victoria-logs-single-server-0` workload and PVC, and the corresponding vmagent scrape targets before restarting anything. Alloy persists file positions in `/var/lib/alloy`, but its sender queue is memory-only; prolonged sink outages can exhaust the bounded retry window.

Restarting Alloy while its sender queue contains unsent entries can lose those entries even though file positions survive. If backpressure prevents the tailer from reading files before rotation removes them, the writer's dropped-entry counter does not account for those unread records. Preserve collector state and inspect backend health before restarting a collector during an outage.

The [logging alert rules](../../kubernetes/apps/observability/victoria-metrics-k8s-stack/app/platform-alerts.yaml) provide partial detection. `AlloyNodeLogIngestionSilent` requires zero sent entries over a ten-minute window followed by fifteen minutes in that condition; it cannot detect partial loss while other entries continue arriving. The sustained-retry alert also waits fifteen minutes. Neither provides a guarantee that an alert will arrive before the retry budget is exhausted, and quiet alert history does not establish complete delivery.

The [collector evaluation](../evaluations/kubernetes-log-collectors.md) records delivery measurements and candidate tradeoffs. Alloy remains the deployed collector; its experimental writer WAL is disabled.

## vlagent implementation

The DaemonSet pins the unmodified upstream image `victoriametrics/vlagent:heads-master-0-gff8635e43@sha256:7492cfbb1468432ca9db753bf9c3e4478b298f72945adaa902254627e9e3dba9`, built from `ff8635e43c1dce4fe1d8b4dc5c57bdf3b62db248`. It includes `output_stream` (upstream #1791), which the tested v1.52.0 release lacks. There is no downstream patch or custom image build. Requalify image upgrades against the delivery and compatibility fixtures.

Stock vlagent flattens application JSON into top-level fields. Collector metadata remains under `kubernetes.*`, with static `cluster=k8s-prod`. An application emitting the same `kubernetes.*` stream keys can cause backend rejection; see the [diagnostic reproduction and production audit](../evaluations/kubernetes-log-collectors.md#metadata-collision-supported-diagnostic-output-2026-09-23). This is a documented upstream limitation, not a prerequisite to fork or switch collectors. Avoid treating arbitrary payload fields or labels as a security boundary. The rejection path currently logs a warning without a dedicated drop counter; inspect backend warnings when diagnosing discrepancies. Upstream [#1603](https://github.com/VictoriaMetrics/VictoriaLogs/issues/1603) and [#1286](https://github.com/VictoriaMetrics/VictoriaLogs/issues/1286) track duplicate-field handling; open [#1664](https://github.com/VictoriaMetrics/VictoriaLogs/pull/1664) is not a deployed fix.

vlagent reads the kubelet-managed `/var/log/containers` symlinks and their `/var/log/pods` targets, both read-only. Discovery is scoped to the current node and uses exact container IDs; this covers static mirror pods without reconstructing paths from their API UIDs. The root owner-read exception drops all capabilities, uses RuntimeDefault seccomp and an immutable root filesystem, and exposes neither host PID nor host networking. RBAC permits pod get/list/watch, node get and namespace list. The observability namespace baseline permits DNS, API access and intra-namespace traffic; the workload policy records metrics ingress and backend egress. Cilium policies are additive, so this does not restrict the broader namespace baseline.

Checkpoints and the remote-write queue persist together under the node-local `/var/lib/vlagent` hostPath. Each node has a 4 GiB compressed queue budget. This is a payload limit, not a filesystem quota: leave at least another 1 GiB for segment allocation, checkpoints and operational headroom, in addition to the node's normal free-space reserve. A node replacement or disk loss loses this state; a PVC shared between nodes would not make their checkpoints interchangeable. Do not delete, move or concurrently open an active queue.

### Query compatibility

New stream identity is `cluster`, `kubernetes.pod_namespace`, `kubernetes.pod_name`, `kubernetes.container_name`, and `kubernetes.pod_node_name`. Service labels remain ordinary metadata: grouping at query time does not add a service facet to `_stream`. `output_stream`, application severity and request IDs are not stream fields. New application fields use their upstream top-level names; retained Alloy fields remain under `msg.*`. `_msg` uses the same `message,msg,log,event,record.message` precedence as Alloy. ANSI cleanup applies to `_msg`. CRI partial stdout/stderr records are reconstructed independently; unrelated multiline application events remain separate. Stock timestamp parsing is retained: recognized JSON time fields and klog timestamps supply `_time`; CRI time is the fallback when no valid parsed timestamp exists. Application clock skew can therefore affect the query window. The delivery fixture uses current timestamps and checks them against a separate `emitted_at` value.

The provisioned **Kubernetes logs** Grafana dashboard uses the [shared compatibility pipe](../../scripts/logging/compat.logsql). It aliases Kubernetes namespace/pod/container/node, derives service from the recommended app label, then legacy app label, then container, and aliases `output_stream` to `stream`. It supports retained Alloy rows with the same query. Explicit JSON/klog severity, credible logfmt with a message/time companion, and the measured Broadsheet, Bambuddy and MCPHub headers normalize to `trace`, `debug`, `info`, `warning`, `error` or `critical`. Unknown severity and continuation lines stay unknown. stdout/stderr never implies severity. App source-format changes remain with #485 / #556.

For Explore or VMUI, begin with a narrow time and authoritative namespace filter, append the shared pipe, then filter or group the resulting aliases. Examples of final pipes are `| filter service_name:=bambuddy stream:=stderr`, `| filter level:in(error,critical)` and `| stats by (namespace,service_name) count()`. Before the compatibility pipe, select both schemas with `(kubernetes.pod_namespace:=printing OR namespace:=printing)`. A raw `namespace:=printing` query alone only selects Alloy history. The Grafana datasource rules color both new `level` and retained `msg.level` values; they cannot parse logfmt by themselves. Use the dashboard or compatibility pipe for the full severity workflow. The external VMUI handoff and 1,000-line default remain configured.

Pod labels are cached while a file is tailed. Prefer replacing a pod when changing its logging identity; otherwise drain the collector queue and restart it to refresh metadata. New rows do not contain Alloy's `filename`; use authoritative pod/container/node fields to locate the source. Retained historical filename queries still work. Fields parsed by klog other than `_msg` are top-level fields in new rows.

### Buffer capacity and monitoring

Size from per-node compressed input, including metadata, using `uv run scripts/logging/measure-input.py --kubeconfig <path> --namespace observability --selector app.kubernetes.io/name=vlagent --seconds 300`. It uses a Prometheus parser so spaces inside label sets cannot turn nonzero samples into zero. Discard intervals with restarted collectors, initial history replay, active flood fixtures or counter resets. The seven-day production baseline measured 1.07–1.40 million rows and 180–212 MB of message text per node; message text excludes metadata and is not the compressed queue rate. A 120-second sample on September 23 measured 316, 356 and 1,094 compressed bytes/second across the three nodes, including the countable drill on node 1. At four times that maximum rate, a 24-hour outage needs about 378 MB; 4 GiB supplies over eleven times that incident budget. This deliberately includes synthetic overhead, but does not cover unbounded storms. Recheck representative working-day and incident rates after cutover; do not interpret a short sample as a days-long guarantee.

The PodMonitor produces `job=vlagent` with a `node` label. Alerts detect missing selected-node collectors, unread source silence, sustained backlog, 75% queue occupancy, persistent-queue evictions and rejected remote-write packets. Dropped-block and dropped-byte counters represent compressed queue loss, not a row count, and fire without a `for` delay. Backend ingestion requires production `job=victoria-logs-single-server` and accepts Loki during transition plus `nativeinsert` after cutover; collector/scratch ingestion cannot satisfy it. Existing backend rejection, PVC, read-only and stream-churn alerts remain. Alloy rules remain until rollback is retired and compare target count against the Alloy DaemonSet's desired nodes.

The 1,500 new-streams/hour envelope is retained deliberately: the new schema contains one identity per pod/container/node, with no per-event values or extra stdout/stderr split. Initial adoption adds roughly one stream per existing container, on top of the measured prior peak of 819/hour. Check the actual first-node and whole-cluster churn before proceeding; lower the threshold after the schema transition if the production baseline supports it.

A nonzero exit reports missing, unexpected or duplicate records. The time bounds must cover generation and recovery. Do not suppress failures or interpret an empty queue as complete delivery.

Fault injection is confined to the scratch backend and exact scratch collector container IDs. Stop only `deployment/vl-vlagent` in `log-drill`, start the finite fixture, optionally terminate the selected scratch collector process, restore the backend, verify restart state and wait for its queue to drain before comparing IDs. Save the original scratch deployment and collector specs first, and restore the backend even if the test fails. Never reboot a node or interrupt the production backend for this collector test.

The SIGKILL result is one observed run, not an exactly-once guarantee or a worst-case bound. A first attempted kill lacked timely termination confirmation and was excluded from the qualification counts. The earlier downstream-patched experiment lost 42 of 2,400 records; it does not establish a stock-image loss rate or mechanism.

Actual alert receiver delivery, production canary validation, acceptance of measured recovery limits and scratch cleanup remain rollout gates. Node/disk failure is not tested. Persistent queue eviction counters measure overflow and cannot prove absence of other loss paths.

## Staged rollout and rollback procedure

This is the procedure to execute **after separate merge and rollout approval**. It is not a record that rollout has happened.

1. Verify the PR's final image digest, scratch results and accepted abrupt-loss/duplication limits. Verify all nodes, storage and Flux resources are healthy. Save a narrow production query window for comparison, ensure VictoriaLogs has headroom, and inspect collector drop/retry metrics. Confirm no node is already labelled `logging.home.kelch.io/collector=vlagent` unexpectedly.
2. Merge the reviewed implementation. Wait for Flux and Grafana provisioning. The vlagent DaemonSet should have zero desired pods; Alloy should still have one per node. The affinity change may roll Alloy, so perform this while its writer is healthy and retries/drops are zero. Keep the existing Alloy `/var/lib/alloy` state for rollback.
3. Select only the canary node: `kubectl label node k8s-prod-1 logging.home.kelch.io/collector=vlagent`. Alloy's DaemonSet excludes selected nodes; vlagent includes them. DaemonSet controllers are independent: a short overlap or gap is possible. Fresh vlagent checkpoints read existing current files from the beginning, so initial replay duplicates retained Alloy history. This is a bounded transition cost, not exactly-once delivery. Record the transition times, Alloy termination, vlagent readiness, replay counts and current log arrival before proceeding.
4. Verify the selected node's `up{job="vlagent"}`, zero queue loss, decreasing/zero backlog and source input. Check current application and static-pod logs, JSON/logfmt/source-specific severity, stdout/stderr, long CRI records, Kubernetes field aliases and timestamps through the provisioned dashboard and VMUI. Compare a fresh finite numbered fixture against its expected set; do not use aggregate production counts as proof of completeness. Verify the receiver gets both a controlled firing and resolved pipeline test alert, preserving only sanitized evidence. Do not alter the production backend to test outage handling.
5. Soak the canary for a representative workload period, then repeat one node at a time for `k8s-prod-2` and `k8s-prod-3`. Stop on missing logs, persistent backlog, loss counters, unexpected duplicates or query failures. Do not proceed merely because the pods are Ready. Recheck capacity and stream creation during and after replay.
6. After explicit acceptance of the full cutover, remove Alloy's Flux resource, manifests, transitional rules and obsolete validation in a follow-up change. Keep retained VictoriaLogs data and its compatibility queries through retention. Confirm all remaining collectors, dashboards and alerts work without Alloy before pruning its node-local state.

For rollback, first restore backend health and wait for vlagent's pending data and in-memory block gauges to reach zero. Remove the selected node's label: `kubectl label node k8s-prod-1 logging.home.kelch.io/collector-`. Verify vlagent terminates gracefully and Alloy resumes from its retained positions. The resumed Alloy can replay logs since it was stopped; logs already rotated away while Alloy was stopped cannot be recovered by its checkpoints. Record the replay window and revalidate fresh delivery. If the backend is still unavailable, preserve vlagent state and obtain a recovery decision before switching collectors: node selection does not drain a queue after its process has stopped. Never run two vlagent processes against the same hostPath.

### Scratch disposition and cleanup

Preserve only sanitized counts, image/config hashes, metric deltas and query assertions in the issue/PR. Never commit raw application exports. Keep the scratch resources while final acceptance or recovery investigation is outstanding. Inventory `log-drill` DaemonSets, generators, debug pods, Services and PVCs before deleting anything; stop generators, restore every scratch backend, and verify pending queues are drained first. Delete only that approved inventory. Use short-lived per-node cleanup pods with exact read/write hostPath mounts after all corresponding collectors are gone to remove `/var/lib/alloy-drill`, `/var/lib/alloy-drill-wal`, `/var/lib/vector-drill`, `/var/lib/vlagent-drill` and `/var/lib/vlagent-583` and `/var/lib/vlagent-583-stock` **only when each path has been verified against the live manifests**. Never mount or delete `/var/lib` wholesale. Check every node, then remove the cleanup pods and scratch cluster RBAC. Production `/var/lib/alloy` has a separate rollback-retirement gate; production `/var/lib/vlagent` must remain. Record verified absence of workloads, PVCs and each approved node-local directory before closing #583.
