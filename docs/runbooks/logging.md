# Kubernetes logging

All Kubernetes container stdout/stderr is collected node-locally by Alloy from `/var/log/pods` and stored in VictoriaLogs, which is the only log backend.

## Query logs

- **Grafana Explore:** `https://grafana.home.kelch.io/explore` — select the `VictoriaLogs` datasource. This is the normal single-pane entry point. The query editor's `Run in VMUI` action carries the current query and time range to the external VMUI, and `View as JSON` is useful when the complete structured row is more useful than the selected `_msg`.
- **VictoriaLogs VMUI:** `https://vlogs.home.kelch.io/select/vmui/` — use the native LogsQL explorer and live-stream view. The bare hostname redirects here.

Grafana authenticates through its native `auth.generic_oauth` integration and dedicated Kanidm client; VictoriaLogs VMUI uses the OIDC middleware on its HTTPRoute. Useful LogsQL starting points are `namespace:observability`, `service_name:grafana`, `level:in("error", "critical")`, `stream:stderr`, and `namespace:observability | stats by (service_name) count()`. The time picker supplies the query window.

## Field model

Current rows use `cluster`, `namespace`, `service_name`, `pod`, `container`, and `node` as their stream identity. Alloy derives `service_name` from `app.kubernetes.io/name`, then legacy `app`, then the container name. `app_instance` preserves `app.kubernetes.io/instance` when present, but remains an ordinary field because it normally identifies an application or Helm release rather than a unique OpenTelemetry service instance.

Alloy normalizes explicit JSON or credible logfmt severity aliases to the Grafana-native top-level `level` values `trace`, `debug`, `info`, `warning`, `error`, and `critical`; fatal and panic aliases fold into `critical` while the original payload remains intact. `level` is an ordinary VictoriaLogs field rather than part of stream identity. Grafana also has bounded compatibility rules for retained rows whose pre-normalization severity exists only in `msg.level`; no general message-text inference is used.

Structured application fields are stored below `msg.*`, preventing payload keys such as `namespace` from replacing Kubernetes metadata. VictoriaLogs derives `_msg` from `message`, `msg`, `log`, `event`, or `record.message` after applying that prefix; non-JSON lines remain unchanged in `_msg`. Alloy strips ANSI terminal color escapes after reconstructing CRI partial records so stored messages remain readable and searchable.

Use ordinary field filters for `app_instance`, `level`, `filename`, and `stream`. For example, `stream:stderr` works across both pre-hardening and current data, while a stream selector such as `{stream="stderr"}` matches only older rows where `stream` was part of `_stream`.

Grafana and all three Traefik instances emit their supported JSON console/access-log formats. Other applications keep their native output until a measured source-specific change is justified. Do not add a global multiline rule: CRI partial records are already reconstructed, and legitimate separator output can resemble continuation lines. Likewise, do not infer stored severity from arbitrary words such as `error` or `info`; an honest unknown level is safer than a false classification.

Retention is nominally 30 days, but VictoriaLogs begins deleting the oldest partitions at 80% disk use. The effective retention is whichever limit is reached first.

## Pipeline failures

Metrics-native rules page through VMAlertmanager when an Alloy target disappears, a node stops sending entries, retries persist, either layer drops data, VictoriaLogs becomes read-only or nearly fills its PVC, ingestion goes silent, or stream creation exceeds the measured rollout envelope. These alerts deliberately depend on the metrics path rather than querying the log backend they diagnose.

If an alert fires, inspect the affected Alloy component graph and writer metrics, the `victoria-logs-single-server-0` workload and PVC, and the corresponding vmagent scrape targets before restarting anything. Alloy persists file positions in `/var/lib/alloy`, but its sender queue is memory-only; prolonged sink outages can exhaust the bounded retry window.

## Durability posture (#581 evaluation, 2026-09-23)

Retaining Alloy is a measured decision grounded in this cluster's actual operations, not momentum. The #581 evaluation (superseding the replatform proposal in #575) asked three decision-first questions and answered each with evidence from the live cluster and a disposable drill namespace.

**1. Is the durability gap real here? No.** Over 30 days of VictoriaMetrics history the pipeline recorded zero ingestion-silent spans, one VictoriaLogs restart (absorbed in seconds — VL starts in milliseconds and collectors buffer through it), six collector-target gaps totaling ~60 minutes (four of 5 minutes, plus the 08-27 node reboots — during which the rebooted nodes were not producing logs, and position-based catch-up recovered the rest), and zero durability alerts fired. At the cluster's real rate (~55–75 rows/s), ten minutes of outage equals roughly 30k entries ≈ 10–15MB, and no observed event has ever come close to exhausting Alloy's ~10-minute retry window. The gap is a paper risk at this scale.

**2. Does any candidate preserve the field model on the real estate? Vector does, at real cost; vlagent gets close at query time.** Replaying live production traffic through each collector into scratch VictoriaLogs backends: Vector achieved exact query parity with the incumbent pipeline (`service_name:grafana` 211/211/211, `level:in("error","critical")` 363/363/363 across prod, drill-Alloy, and Vector arms; identical Talos static-pod config-hash file attribution; identical label-less Longhorn grouping; traefik attribution 12,125/12,127/12,127 rows) — but only via a bespoke VRL pipeline replicating #487 severity alias-folding and the 3-way `service_name` fallback, which becomes permanent maintenance plus the Elasticsearch/jsonline ingestion shim. vlagent's gaps are narrower than collector flags suggest but irreducible at ingestion: LogsQL's query-time `coalesce` pipe reproduces the 3-way `service_name` fallback with exact value parity (identical top-25 group sets, counts within 0.01% on live traffic), and severity alias filtering is expressible per-query via `level:~"(?i)^(err|error|severe|...)$"` — vlagent even auto-detects klog severity prefixes the incumbent leaves honestly unknown. What cannot be recovered at query time: `stream` (stdout/stderr) and `filename` are never collected (~18 query references in this repo affected), the ingestion-time stream identity differs from the incumbent's, pod-label changes require a collector restart (measured: a changed label was invisible 100s later), app payload keys are stored at top level so `namespace`/`pod`/`container` lose their Kubernetes-authoritative meaning, and every query grows `coalesce`/regex chains instead of plain field filters.

**3. What do real operations lose? Nothing, on any candidate.** A VictoriaLogs upgrade-style restart delivered 1790/1790 numbered fixtures on all four arms including baseline Alloy; a deliberately chaotic double-restart with mixed old/new backends likewise lost nothing on any arm. Sustained unavailability beyond ~10 minutes is the only loss mode, and no real operation produces it.

Mechanical drill results (for the record): with all collector pods deleted mid-outage against a down backend, vlagent and Vector replayed 100% of 12,839 numbered fixtures while both Alloy arms replayed 51% — the Alloy WAL was enabled, active, and still replayed nothing across the restart. Under saturation (~1.4MB/s, ~2,000× real volume) vlagent's documented drop-oldest engaged while its `pending_data_bytes`/`queue_blocked` metrics misreported 0, and Vector's disk buffer silently stopped accepting at cap with no drop counter or log line — neither candidate's saturation loss is observable through its own metrics. Full evidence in #581.

Accepted limitations of the retained pipeline: beyond ~10 minutes of continuous backend unavailability, entries are lost (retry exhaustion), and a second uncounted loss mode exists — `loki.write` `block_on_overflow` backpressure stalls the file tailer, kubelet/containerd log rotation deletes unread files, and `loki_write_dropped_entries_total` does not increment; node-silence alerting is the coverage for both. Revisit the collector choice only if sustained multi-hour backend outages become a real operational pattern here, or if vlagent grows collection-side transform capability — the migration budget then is a query-surface migration (rewriting the ~40 `service_name`/`filename`/`stream`/`level` query references as `coalesce`/regex chains or accepting the two lost fields), stream-identity rework, Grafana provisioning, successor CI contract, and new loss-detection, since candidate queue metrics misreport drops. Do not enable Alloy's experimental `loki.write` WAL: it is restart-lossy, silently age-deletes undelivered data at `max_segment_age`, and holds roughly one hour of ingest on disk with no size cap.
