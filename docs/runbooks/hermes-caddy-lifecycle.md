## Authority and contract

**Future owner decision:** approve that merging a Caddy image promotion PR authorizes automatic Caddy-only HTTPS interruption and automatic restoration on failure. Preparing this code does not grant that standing authority. Installation, the first attended cutover, owner-assisted acceptance and a live rollback/forward drill require a separate commissioning window. Main has no enforced check gate; review and CI are repository policy, not a guest GitHub API dependency.

The fixed root-installed `/usr/local/sbin/hermes-caddy-update` shallowly fetches public main and parses exactly `services.caddy.image` from the desired overlay. It never executes fetched files, updates itself, applies a fetched Compose/Caddyfile, or reapplies Hermes. An older reviewed digest remains valid when newer source inputs are on main. `candidate` is discovery only; pulls and receipts identify immutable digests. Changes to installed script/Compose/runtime need separate reviewed installation.

The project remains `/opt/hermes`, project `hermes`. `.env` selects `COMPOSE_FILE=compose.yaml:compose.caddy-image.yaml` and `COMPOSE_PROJECT_NAME=hermes`; plain Compose commands and relative mounts keep working. See Docker's [Compose environment reference](https://docs.docker.com/compose/how-tos/environment-variables/envvars/). The base retains a local image fallback without `build`. The installed overlay initially names the guarded legacy image, independently of the desired Git pin.

Preserve `/srv/caddy/data` and `/srv/caddy/config`, numeric ownership 1000:1000 and the existing ACME account. `/srv/caddy/.env` stays root-only; the updater never opens it or copies its values into state. Compose loads it only when recreating Caddy. Keep UID 1000, host networking, no init, read-only root, only `NET_BIND_SERVICE`, `no-new-privileges`, tmpfs, Caddyfile and all mounts unchanged. Hermes's managed config and runtime secrets are unrelated.

## First cutover and acceptance

1. Confirm desired digest PR/native qualification and owner approval, public availability, cached legacy ID and the separately approved interruption window. Disposable Docker tests prove automatic failure paths; do not deliberately break production.
2. Keep the timer disabled. `sudo hermes-caddy-update resume` clears pause; `sudo hermes-caddy-update run` performs the attended transaction. Commands serialize; `pause` cannot interrupt an active transaction. Let it finish or follow recovery below. Record measured outage and recovery instead of assuming a 30-second bound.
3. Confirm verified hostname HTTPS, certificate validity exceeding seven days, Docker health, zero restarts/failing streak/zombies and bounded process count. The readiness budget is 30 seconds **after Compose returns**, followed by five minutes of health/TLS/process checks. Certificate renewal is accepted; fingerprints are informational. Capture about nine natural Docker checks, process samples and unchanged ACME account/state identity for first commissioning.
4. The owner signs in to the dashboard and confirms authenticated `/api/ws` and `/api/pty` 101 upgrades plus an interactive PTY. Store no owner session/admin credential in automation. Record unchanged Hermes ID/start and managed config. Automated status and stub WebSocket checks do not prove this live acceptance.
5. With separate live-drill approval, `sudo hermes-caddy-update rollback` pauses and restores the cached predecessor using `--no-deps --no-build --pull never -t 1 caddy`. Verify TLS and authenticated functions. `sudo hermes-caddy-update retry` clears quarantine; `resume` and an attended `run` then restore the desired Git digest. Record both interruptions. Manual rollback stays paused to prevent unattended roll-forward.
6. After standing authority, acceptance and notification testing, `sudo systemctl enable --now hermes-caddy-update.timer`. It runs two minutes after boot and five minutes after a run ends; the oneshot ceiling is 15 minutes. Verify no-op runs preserve Caddy/Hermes IDs. Exercise one controlled heartbeat `/fail` and recovery with the owner and confirm both existing notifications. Pause the single check during planned updater downtime; any ping resumes a paused Healthchecks check.

## Transactions and recovery

Each run takes a nonblocking exclusive lock. Before stopping Caddy it pre-pulls the exact amd64 digest, checks RepoDigests, OCI source/revision and UID, and adapts the installed Caddyfile offline using a dummy token. It verifies the current image's cached ID and health. One atomically replaced `pending.json` records target, predecessor and Hermes identity before changing the overlay. Compose changes only `caddy`, with dependencies, build and pull disabled. Retain current/previous local images and public digests: no pruning or registry cleanup is automated. Rollback uses guarded local bytes without registry access.

At boot and every timer run an open pending transaction conservatively restores its predecessor before fetching main, even when paused. Readiness/settle failure restores the predecessor and quarantines the rejected reference in `failed.json`. Restarts and unrelated main commits do not retry it. Reverting Git to the prior accepted digest works normally. `retry` explicitly clears quarantine but leaves pause unchanged. A quarantined desired digest remains an alert condition while its predecessor serves.

An exceeded Compose client deadline or failed rollback marks pending `recovery_required`. Automatic runs then fail and perform no more mutations. **Do not delete pending to silence it.** Disable/pause the timer, inspect selected Caddy state and ensure no prior Compose/Engine operation remains in flight. Reconcile predecessor reference/ID if necessary, then use attended `rollback` to retry recovery; it keeps pause set. If missing, pull its recorded public digest under attended recovery and verify the local ID before retrying. Never rebuild an approximate predecessor or replace its reference with different bytes. Legacy recovery needs its retained local image or a VM backup.

Root-only `/var/lib/hermes-caddy` contains `current.json`, `previous.json`, `last.json`, `failed.json`, `pending.json` and `receipts/*.json`. Receipts record main SHA, image reference/ID, OCI revision/run, timestamps, selected health/process data, certificate fingerprint, result and sampled interruption. Sampling observes a 0.25-second interval plus request latency; it is neither a watchdog nor a downtime guarantee. A hung Engine can exceed readiness; the updater stops mutating for recovery. Manage receipt retention manually and retain predecessor images.

Idle polls still check Docker health/restart/streak, verified HTTPS/certificate margin, `pids.current` (maximum 128) and zombies, catching slow leaks between rollouts. A healthy no-op or accepted rollout sends one success heartbeat; rejection/quarantine/recovery failure sends `/fail`. Paused runs send neither. Missing monitoring is a commissioning blocker.
