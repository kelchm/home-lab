## Desired UniFi change

For each intended routed source subnet (`10.32.{1,5,10,21,25,30,90}.0/24`), evaluate the fresh policy order to each destination `10.32.20.111/32` and `10.32.20.112/32`. Where blocked, add only an IPv4 **allow, UDP, source port any, destination port 123**, with those exact source subnets and two destination IPs, ahead of the specific blocking policy. Split by actual source/destination zones if needed; use current zone IDs. Preserve existing policies and established/related return handling, following [UniFi's zone-policy and return guidance](https://help.ui.com/hc/en-us/articles/115003173168-Zone-Based-Firewalls-in-UniFi). If UniFi generates a paired return, verify its parent relationship and state match; do not add an unrestricted reverse initiation rule. Same-subnet Infra Mgmt clients need no routed gateway exception; the Pi ACL/firewall still applies. Do not permit all of Infra Mgmt, broaden a protected-network rule, add NAT/redirects, change WAN routes, or add TCP, IPv6, Guest or Remote Admin access.

The exact new-rule count and placement remain a decision on the missing read-back, particularly for Cameras isolation and Workloads containment. Return that small per-policy delta with current IDs before requesting activation; there is no declarative UniFi deployment artifact in this repository.

[Ubiquiti documents a predefined NTP Server option 42](https://help.ui.com/hc/en-us/articles/360012097513-UniFi-DHCP-Server). [RFC 2132 §8.3](https://www.rfc-editor.org/rfc/rfc2132.html#section-8.3) defines it as a list of IPv4 addresses, in preference order, with four bytes per address. For each intended network actually running the DHCP **server**, set that predefined option to `10.32.20.111`, `10.32.20.112` in that order. Do not enable DHCP, alter relay networks, or add an option on Guest/Remote Admin. Preserve scopes, lease times, DNS, gateways, boot/custom options, reservations and every unrelated field. Prefer the supported UI if writes are UI-only; read the saved network object back afterward. The current private API's NTP field names, value type and enable semantics are **unverified**; no payload is proposed until they are observed. Do not invent fields or create a second custom option 42 alongside the predefined one.

DHCP advertisement does not configure the gateway's own clock, static-address clients or clients that ignore option 42. It also does not promise that a client honors preference order. DHCP advertises only the two local services; their accepted chrony configuration supplies public upstream alternatives. Explicit Talos clients additionally retain their existing public servers. Other explicitly configured infrastructure clients need their own reviewed change.

## Talos behavior

The proposed list is `10.32.20.111`, `10.32.20.112`, `162.159.200.1`, `162.159.200.123`. For the pinned v1.14.4, the [SNTP implementation](https://github.com/siderolabs/talos/blob/v1.14.4/internal/pkg/ntp/ntp.go) tries the resolved list in order when choosing a server, then keeps querying the last successful server. A query failure triggers another search, skipping the just-failed server for that pass. A changed list resets that remembered server and wakes the loop. A working public server can therefore remain selected after local service recovers; list order is not strict ongoing preference or automatic failback. Talos does not run chrony's multi-source comparison. Public addresses remain alternatives if local queries fail, not concurrently cross-checked references.

The [time controller](https://github.com/siderolabs/talos/blob/v1.14.4/internal/app/machined/pkg/controllers/time/sync.go) reconciles a changed server list live. The existing `machine.time` form disables NTS ([provider implementation](https://github.com/siderolabs/talos/blob/v1.14.4/pkg/machinery/config/types/v1alpha1/v1alpha1_provider.go)); keep it for these plain-NTP Pis. No reboot, daemon restart or time step is requested by this procedure. Talos can itself step an offset over 400 ms, so stop on a large offset or unexpected clock jump. `TimeStatus.synced` is sticky once established (and can also be satisfied by a boot timeout); inspect fresh NTP responses and clock adjustments, not that flag alone. [`talosctl time`](https://github.com/siderolabs/talos/blob/v1.14.4/internal/app/machined/internal/server/v1alpha1/v1alpha1_time.go) issues a new query and defaults to the first configured server; it is not evidence of which server the background syncer selected.

## Rollback

For a failing Talos node, restore the previous public-only list (`162.159.200.1`, `162.159.200.123`) in the source patch on the rollback branch, then regenerate and use the same `task talos:apply-node IP=<node-ip> MODE=no-reboot` confirmation path for that node. Require only that list difference, the same encryption preservation and a fresh successful public-source adjustment before advancing. Reverting the Git commit alone does not restore live Talos state; never apply an old generated machine configuration wholesale.

For DHCP, restore each changed network's recorded previous NTP option values and enable state, preserving the rest of the current object, then read back and check a representative client's next lease. Withdraw local advertisement and restore explicit clients before disabling any new gateway allowance they rely on. Remove/disable only the new NTP forward policies and their verified generated returns by current IDs/parent relationship; preserve all pre-existing policies and routes. Record acceptance or rollback evidence in #1031 and update this runbook's verified state after the operation.
