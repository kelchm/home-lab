# GLM-5.3-Flash recipes through SparkRun

These recipes serve `GLM-5.3-Flash-EXL3` across two DGX Sparks at `http://10.32.21.31:8888/v1`. SparkRun 0.3.10 owns model/image distribution, fabric detection, containers, runtime caches, readiness, warmup, logs, stop, and native benchmarking for both engines. TensorFold uses the adjacent external runtime adapter. These hosts are outside Flux. Check actual host state before launching; other experiments can use either GPU.

The September 30/October 1 candidates are under evaluation in [#645](https://github.com/kelchm/home-lab/issues/645) and [PR #648](https://github.com/kelchm/home-lab/pull/648). The versioned Mia TensorFold profiles retain the running v1.2 config, the v1.5 and v1.8 server candidates on the same stock TR3 weights, and the v1.5 and v1.8 published TP2 defaults with Mia’s own weights. The v1.5 and v1.8 images and site guards are source-verified; no v1.5 or v1.8 profile has started on the Sparks. At the last read-only check on October 4 both Sparks still ran v1.2, which passed native boot/shape warmup, the live API/client gates, all 13 long-session cases and actual C4 output growth on October 1. The intermediate v1.3 candidate was source-verified but never live-qualified; its only launch aborted before containers started. Refreshed Mia/vLLM v7 passed native boot, CUDA/protocol and client-accounting checks, but only 18/20 agent cases. Its 13-case comparison completed with valid telemetry; headroom was below target and the short arrival during long prefill took 10.35s. TensorFold W20 remains a diagnostic comparison, and the exact September 19 Mia recipe, image and prepared mod remain the older retained fallback; the running v1.2 recipe is the immediate rollback for a v1.5 or v1.8 trial. Provisional trials require fresh healthy-link/idle checks and abort on new carrier drops, lost telemetry or sustained sub-2 GiB headroom; the separate defect in [#649](https://github.com/kelchm/home-lab/issues/649) remains open. These are evaluation candidates; raw receipts stay outside git.

This compares complete recipes: the draft weights, arithmetic, scheduler and cache implementation differ. Normal evaluation is C4 at 128k–262k, with C1/C2 controls. Four 262k prompts plus reserved output exceed W20's shared pool and must queue. Mia TensorFold allocates prompt extents, then grows them during decode; its measured startup pool is required before making a capacity claim. C8 is a secondary short/warm workload. None of these recipes promises four simultaneous 850k requests.

W20's output reservations matter before that boundary: four 250k prompts with 32,768 output tokens and the 64-token reserve require at least 1,131,328 pool tokens. An 8,192-token output budget puts that arithmetic total at 1,033,024. The 256-token primary timing cases do not qualify C4 at the client's full 32k output limit. The full suite includes a 250k case with that budget and a short expected answer. Mia's kit does not reserve that whole budget at admission, so a separate growth case requires actual long output. TensorFold v1.2 completed four 250k prompts with 4,096 actual output tokens each; full 32k replies remain unqualified. Inspect admission, pool growth, pauses and tail latency before choosing client defaults.

### Versioned Mia TensorFold profiles

The `mia-tensorfold-glm53-exl3-tp2/` directory groups the shared Mia TensorFold server kit, GLM-5.3-Flash model, EXL3 format and TP2 topology. Filenames repeat the model, format and topology for identification outside the folder, followed by Mia’s TensorFold kit release (`mia-tf-v1.x`), quantization creator and request context ceiling: `glm53-exl3-tp2-mia-tf-v1.2-bmm-850k`, `glm53-exl3-tp2-mia-tf-v1.5-bmm-850k`, `glm53-exl3-tp2-mia-tf-v1.5-mia-1m`, `glm53-exl3-tp2-mia-tf-v1.8-bmm-850k` and `glm53-exl3-tp2-mia-tf-v1.8-mia-1m`. The version is the kit release whose image the recipe pins, not the engine version: v1.5 and v1.8 both build on TensorFold 0.6.0 and differ in Mia’s patch set. BMM is Brandon M. Music ([Hugging Face: `brandonmusic`](https://huggingface.co/brandonmusic)), whose TR3 checkpoint is mirrored by Mia; `mia` selects Mia’s own calibration, the kit’s standard checkpoint. The `850k` recipes allow 850,000 tokens with an 18.5 GiB reserve; `1m` allows 1,048,576 tokens with the published 14.5 GiB reserve and window settings. Each file is a complete recipe. SparkRun derives its name from the filename stem, which matches `metadata.profile` and remains unique across the five recipes; select it by its path under the family directory.

`metadata.upstream_release`, `metadata.weights`, `metadata.weights_variant` and `metadata.serving_profile` record the kit release, quantization creator, checkpoint variant and settings preset separately; all five use EXL3 at 4bpw. `recipe_version: '2'` is SparkRun’s schema version and stays 2 in all five files. All profiles keep the served API name `GLM-5.3-Flash-EXL3`, so the same client requests work after switching the active recipe. Use one profile at a time on the same two hosts.

`glm53-exl3-tp2-mia-tf-v1.2-bmm-850k` preserves the running instance’s serving, distribution and cache settings, recovered from its retained recipe. Its original configuration passed the October 1 live gates; the newly named file and packaged mod have only local validation. `glm53-exl3-tp2-mia-tf-v1.5-bmm-850k` is the incremental server update: stock TR3 `25a44fdb`, DFlash2 `bf582e4e`, TP2/PP1, C4, an 850k request ceiling, 32,768 default reply budget, 18.5 GiB reserve, 12.5 GiB extra-cache cap and the same vision/input bounds. `glm53-exl3-tp2-mia-tf-v1.5-mia-1m` selects Mia’s new checkpoint and published TP2/C4 serving defaults, including the 1,048,576 window and 14.5 GiB reserve. `glm53-exl3-tp2-mia-tf-v1.8-bmm-850k` is the v1.5 TR3 recipe on the v1.8 image: the same weights, drafter, capacity limits and launcher values, plus one setting, described with the v1.8 provenance below. `glm53-exl3-tp2-mia-tf-v1.8-mia-1m` is the v1.8 kit’s published two-Spark recipe adapted to SparkRun: the same standard Mia checkpoint, drafter and limits as the v1.5 Mia-weights recipe, on the v1.8 image, with every engine setting the v1.8 launcher exports stated in the recipe. SparkRun’s lifecycle, fabric detection, exact-call-ID/strict-health site guards and 1.2M pool readiness floor remain in the v1.5 and v1.8 profiles; these adapt the upstream serving recipe rather than invoking its launcher, clock controls or window fallback, and the differences that leaves are listed with the v1.8 provenance. C8, steering/abliteration, the Ablit weights and upstream work not yet merged are outside these profiles.

Two kinds of comparison are available. Within a weight family, across kit releases, the weights and limits stay fixed and the server changes: `glm53-exl3-tp2-mia-tf-v1.2-bmm-850k` against `glm53-exl3-tp2-mia-tf-v1.5-bmm-850k` changes the server and launcher defaults; `glm53-exl3-tp2-mia-tf-v1.5-bmm-850k` against `glm53-exl3-tp2-mia-tf-v1.8-bmm-850k` changes the server patch set and the RoCE wait, and against the measured v1.2 everything the v1.5 comparison does as well; `glm53-exl3-tp2-mia-tf-v1.5-mia-1m` against `glm53-exl3-tp2-mia-tf-v1.8-mia-1m` changes the patch set, the RoCE wait and one NCCL variable described below. Within a kit release, a BMM profile against its Mia profile (`…v1.5-bmm-850k` with `…v1.5-mia-1m`, or `…v1.8-bmm-850k` with `…v1.8-mia-1m`) changes weights, request ceiling and reserve together, so it evaluates complete recipes, not weights. A weights-only conclusion requires matched server settings and capacity limits, which no pair here provides. Keep prompts, sampling, reasoning effort, tool/client behavior and output budgets equal; distinguish cold boots from warm replay and record the profile, git commit, model revision, startup pool and both hosts’ memory minima with each receipt.

The versioned mods are self-contained: each includes its own pinned readiness gate, launcher and guard installer. `prepare.py` verifies five tracked helper hashes without copying from a sibling mod, and `run.sh` repeats that check inside the container. The v1.2 lock accepts the old image’s guarded source, the shared v1.5 mod accepts the v1.5 image’s, and the v1.8 mod, shared by both v1.8 profiles, accepts only the v1.8 image’s. Image- and model/revision-keyed SparkRun runtime caches give the five profiles separate persistent cache directories; the v1.2 profile’s is the one the original recipe already uses. To add another release, add an explicitly named recipe and a matching pinned bundle when its image or helpers change; retain the existing profiles.

SparkRun never runs upstream's `start.sh`, and the engine's built-in defaults differ from that launcher's, so the v1.5 and v1.8 profiles set the launcher values explicitly:

| Setting | Engine default | Recipe (v1.5 launcher) | Effect to measure |
| --- | --- | --- | --- |
| `TF_GLM_MULTI_LONE` | 1 | 0 | A lone stream no longer moves to the pool's first rows, so that move no longer evicts idle kept prompts there. It does not address the shared-prefix displacement below; upstream gives up its reported 0.6–0.9% single-stream gain |
| `TF_GLM_CACHE_ENTRIES` | 8 | 32 | More kept prompt states. Upstream estimates 45 MiB of fixed state per entry, about 1 GiB more than at 8. The engine reserves it from the existing 12.5 GiB kept-prompt budget, shrinking the token pool at equal free memory. That is a startup estimate, so still measure both hosts' headroom |
| `TF_GLM_MTP` | 1 | auto | With the DFlash2 drafter loaded, the checkpoint's MTP head is not loaded. v1.2 leaves this unset and its engine defaults to auto, so every versioned profile serves without the head |
| `TF_GLM_CLEAR_THINKING` | 0 | 0 | Stated so the kept-reasoning rendering is deliberate |
| `TF_GLM_FILL_BUDGET_MS` / `TF_GLM_FILL_DRAFTS` | off / 0 | 200 / 1 | A new prompt fills in layer slices between decode rounds: other streams keep decoding, and the arriving prompt's cold first token comes later |
| `TF_GLM_STREAM_SMOOTH` / `TF_GLM_STREAM_SMOOTH_MS` | 0 / default 400 | 1 / 400 | Streamed tokens are paced from a 400 ms playout buffer, so text appears about 400 ms later. Upstream says replies still end when they did and gaps are smoother; neither is measured here |

These are trade-offs to qualify on our workload, not speedups. `TF_GLM_MULTI_WINDOW` remains 32: implicit in the TR3 candidates and explicit in the Mia-weights profiles, matching the launcher at four streams. At C4 upstream’s reserve is 14.5 GiB (19.6 GiB applies only to its eight-stream, 64-row configuration), so the TR3 profiles’ 18.5 GiB is 4 GiB above it.

One cache defect is known in v1.5 and stays in both v1.5 profiles: with `TF_GLM_SHARED_PREFIX=1`, a short conversation that resumes from a system prefix written by an idle long conversation can displace the long conversation's kept prompt even when the pool has free space ([upstream #43](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/issues/43)). Turns still complete; the long conversation re-prefills. Upstream fixed it in v1.6 with the patch from [PR #44](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/pull/44); the v1.5 recipes are not backported, and both v1.8 profiles carry the fix. `TF_GLM_SHARED_PREFIX` stays 1 in every profile, and the live gate below replays that case on whichever server is under test.

`glm53-exl3-tp2-mia-tf-v1.8-bmm-850k` differs from `glm53-exl3-tp2-mia-tf-v1.5-bmm-850k` in the image, its metadata, the mod path and one setting, `TF_ROCE_WAIT_S=300`. The engine waits 20 s for the peer rank's half of a RoCE all-gather before it fails both ranks; upstream's launcher has set 300 s since v1.6, after reports of ranks failing on long prompts while the peer was late, not lost ([upstream #54](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/issues/54), still open). SparkRun does not run that launcher, so both v1.8 recipes state it. The trade-off is deliberate: a late peer costs a slow round, and a rank that is really gone is noticed after five minutes instead of twenty seconds. During that wait the strict health guard still answers 200, because it reports a failed decoder or dead scheduler thread, not a stall. The setting concerns the CX7 inference fabric; it neither fixes nor masks the management-link carrier fault in [#649](https://github.com/kelchm/home-lab/issues/649).

`glm53-exl3-tp2-mia-tf-v1.8-mia-1m` follows the pinned kit’s published defaults, read from [`scripts/config.sh`](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/blob/33b50fde06fd7ea604cbc6a663880068ab1e2ee4/scripts/config.sh) with no `scripts/local.sh` or `.env`. The model and drafter revisions, TP2, the 1,048,576 window, the 32,768 reply budget, four streams, thinking and vision on, picture URLs off, port, served name and image digest are the kit’s, and all 31 engine variables that file exports appear in the recipe with the same values. That includes `TF_GLM_DISPLAY_KV_MIB=0` and an empty `TF_GLM_MAX_QUEUED`, which the engine reads exactly as unset: no admission cap. The seven media bounds and the 1,024-reply/32 MiB kept-reasoning limits the recipe also lists are the engine’s built-in defaults, which upstream leaves unset; they are stated for audit, not tuned. Against `glm53-exl3-tp2-mia-tf-v1.5-mia-1m` the recipe changes the image, its metadata, the mod path and the RoCE wait, states the display and queue defaults, and drops `NCCL_CUMEM_ENABLE=0`, which upstream does not set. The four earlier TensorFold recipes each keep that variable in their own `env`, and the adapter does not add it.

It is an adaptation, not upstream’s launch reproduced bit for bit. What differs, all SparkRun-owned or deliberate:

- Launcher: [`start.sh`](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/blob/33b50fde06fd7ea604cbc6a663880068ab1e2ee4/start.sh) never runs, so its preflight, memory warning, saved logs and smoke test are absent, as are its two recoveries: the retry with a smaller window when the requested one does not fit, and the `SPLIT=0` retry after a first NCCL connection failure ([upstream #36](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/issues/36)). Here a window that does not fit, or that failure, ends the launch.
- Rank command: the mod passes the kit’s serve flags plus `--backend cuda` (upstream leaves the default `auto`) and `--no-update-check` (the kit sets the equivalent variable, as does the recipe).
- Container: SparkRun clears the image entrypoint, so NVIDIA’s entrypoint script does not run, and adds `--user root`, `no-new-privileges` and an open-file limit. Both use host IPC and networking, all GPUs, `/dev/infiniband`, `IPC_LOCK`, unlimited locked memory and the 64 MiB stack.
- Fabric: the ranks meet on SparkRun’s rendezvous address and port 25000 instead of the kit’s link address and 29551. SparkRun detects the NCCL interface, devices and GID index on the hosts at launch; the kit’s own link and two-rail detection does not run, and a dry run does not show the result. Both pin four NCCL channels. Upstream notes that some other NCCL settings kept it on one rail, so read the rail count from the rank logs on a first boot.
- Caches: weights mount at `/cache/huggingface` and compiled kernels go to SparkRun’s image- and model-keyed `/cache/runtime`, not the kit’s per-patch-hash directory. Both serve offline from the local snapshot; SparkRun also sets `TRANSFORMERS_OFFLINE=1`.
- Inert variables: the adapter’s `GLM53_TF_*` settings are for W20 and nothing in the v1.8 source reads them. `NCCL_PASSTHROUGH=1` is carried from the earlier recipes, and neither SparkRun 0.3.10 nor the v1.8 Python source reads it.
- Site additions: the exact-call-ID reasoning guard, the HTTP 503 health mapping, and the readiness hook with its 1.2M pool floor and C4 shape warmup. Upstream’s clock controls stay manual and unused.

Server changes the v1.8 image brings over v1.5, from the pinned changelog:

- Kept prompts under shared prefixes and pressure (v1.6): a resume from a shared system prefix copies those rows into free rows instead of taking over the writer's extent ([PR #44](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/pull/44)); it falls back to the old behaviour when no rows are free or with `TF_GLM_MULTI_LONE=1`, and the recipes keep `0`. A turn whose rows are free but scattered now compacts the pool before evicting another conversation's kept prompt ([PR #62](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/pull/62)).
- Kept-state cap (v1.7.1): shared-prefix states are evicted by recency, repairing a v1.6 regression in which a new agent run re-read its system prompt once the cap was full ([upstream #75](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/issues/75)). v1.5 predates that regression.
- Capacity and cancellation (v1.6, v1.8): requests queued behind four busy streams are dropped when their client leaves, and a stream whose delivery fails frees its slot at once. Capacity refusals before response headers are sent answer HTTP 429 with `Retry-After: 5` instead of a bare 503 or 400 ([PR #48](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/pull/48)), which keeps them distinct from the health guard's 503. Once an SSE response has started, an error stays within that HTTP 200 stream.
- Vision (v1.8): a chat's pictures are decoded once per server instead of every turn, in a host-memory cache that is on by default and capped at 384 MiB of source bytes plus eight canvases ([PR #63](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/pull/63)); text that only quotes the template's picture marker stays text ([PR #64](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks-TensorFold/pull/64)).

## Settings and limits

The [recipe](mia-glm53-exl3.yaml) keeps InstantTensor, EXL3/TR3 target TP2, DFlash2 k=7 with draft TP2, 850,000 context, four sequences, 7,168-token batches, FP8 KV, CUDA graphs, fair mixed-prefill scheduling, and abliteration disabled. Image and model revisions are immutable pins. Source and image are pinned separately; the source revision is not a claim about image build provenance.

`INSTANTTENSOR_BUFFER_SIZE=2147483648` caps loader I/O staging at 2 GiB instead of the installed InstantTensor 0.2.0 TP2 default of 4 GiB. The library automatically reduces I/O depth; the largest target tensor is about 1.18 GiB. This is a loading bound, not a promise of 2 GiB lower steady-state RAM. The refreshed Mia recipe's explicit 11 GiB KV pool governs serving allocation instead of the `.85` utilization setting; the retained control uses 14 GiB. Eight NCCL channels, right-sized indexer workspace, a 1 GiB multimodal processor cache and graph estimation disabled remain; graph execution stays enabled. Dense FP8 `all`, BF16 large-M KDA and compact draft KV follow the coherent current upstream bundle.

W20 uses q4mse non-experts, latent FP8 KV, multi-slot prefill, W19 scratch/NCCL settings, W20 tools, a 2 GiB RAM session store and a 64 GiB NVMe tier per rank. Its shared pool reserves prompt plus output plus 64 tokens per request. Mia TensorFold uses its separate q4/FP8/chunked-KDA, DFlash2/copy-draft and multi-prefill bundle; dense weights and KV are lossy and chunked KDA changes arithmetic. Its pool admits aligned prompt extents and grows them during decode. The 850k ceiling describes one request while pool space is available; slot admission, memory minima, cold-prefill latency and actual decode overlap must be measured. Vision is enabled in all candidates; logprobs and maximum-image/context capabilities are not assumed equivalent.

SparkRun's fit estimate does not account for the full hybrid cache state; use vLLM allocation and host telemetry to judge fit. The 850k allocation/retrieval test completed with cache preemptions and replay, not uninterrupted prefill. 850k is a per-request ceiling, not a promise of four simultaneous 850k requests or responsive long-prefill latency. Idle prefix retention is much smaller than equivalent-token capacity. The vLLM 48-image/1-video and Mia TensorFold v1.2 50-image/4-video maxima, simultaneous maximum-context workloads, general long-context quality and reboot recovery have not been qualified. Mia v1.2 bounds request-wide image/video tokens to 16,384/32,768; our media gate checks five images, not those full maxima.
