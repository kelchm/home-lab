# Vonk Forge evaluation — September 6, 2026

The second pass is in progress. The platform is useful for controlled single-Spark inference: bounded text, tool and vision probes passed, and one complete normal stop/start cycle now works with the evaluated controller fixes. However, starting a long installation interrupted an existing healthy model's public serving route when its observations went stale; background installation alongside inference currently fails this coexistence test. Practical operation also requires recipe corrections, several minutes of startup and explicit checks of the serving endpoint. New online builds remain blocked at the native egress proxy, and dual-Spark execution is unqualified. Successful enrollment, a built image and a running container are separate from inference qualification. The current experiment uses the published recipe-v1 contract; it does not silently upgrade the controller or library to current upstream schemas.

Startup is a material operating cost. This retained-weight start loaded 21.99 GiB of model memory in 28.18s and spent 124.03s initializing the engine, including compilation, profiling and kernel warmup. The runtime reported 22.94s for `torch.compile` and created a fresh cache under the new run's `/outputs/cache`. A successful container start is therefore insufficient evidence that a client can infer, and ordinary stop/start is disruptive for several minutes even without downloading weights.

Long-operation coexistence exposed a separate availability failure. Qwen3.8 model installation began around 12:28:45 UTC; the existing Qwen3.6 run's observation stopped at 12:28:42.013512. At 12:32:59 its route was withdrawn while health/freshness still appeared true at approximately 257 seconds old. At 12:33:45 the exact run was `running / withdrawn / unhealthy`, its observation was 303.65 seconds old, and public inference returned 503 in 26ms. The actual container had neither restarted nor OOMed, and direct runtime health returned 200 in 11ms. The installation continued through normal completion. Both nodes passed all 25 primary file hashes, with the first succeeded operation sample at 13:30:45.775 UTC. Fresh old-Qwen evidence resumed at 13:30:40.257; the route was first observed automatically published at 13:31:36.579. A real routed request at 13:32:14.563 returned HTTP 200 and `READY` in 0.850s. No recovery mutation, lease extension, service restart or follow-on Spark 2 operation occurred. The model is serving again, but this approximately hour-long operation did interrupt availability.

Exact-source inspection confirmed the scheduling cause: the control loop collects observations, then awaits the complete operation before collecting again. Synchronous installation also blocks the telemetry future polled beside control. The separately spawned operation heartbeat continues, preserving the install lease without proving model health. The worker uses a 120-second observation window, while run-health presentation uses 300 seconds; those distinct limits explain the temporarily withdrawn-but-healthy status. The [signed native scheduling proposal](https://github.com/kelchm/vonk-forge/pull/4) separates observation and telemetry tasks from long control operations and serializes credential activation with complete observation cycles. It also handles proven stop/uninstall metadata removal and requires a controller transition correction before native rollout. No freshness threshold or installed agent has changed.

The scheduling proposal passed 92 Linux/amd64 checks with Rust 1.97.1 after explicitly cleaning the diagnostic package build: 13 binary, 68 library, five observation workload and six exact workload tests. An earlier stale cached library result was detected and discarded. The fixtures cover the actual two-worker runtime with synchronous blocking work, credential revocation, shutdown, concurrent stop/read and invalid evidence. Its controller dependency passed 204 tests with six existing skips, plus two independent signed-grant/receipt cases. A late report from a stopped run receives non-authoritative HTTP 425 only after validating its genuine prior evidence; transaction rollback preserves both health rows and grant consumption. Invalid signatures/identities and mixed batches remain rejected. These are source-level results; real uninterrupted serving during a long operation is still unqualified, and inventory still refreshes between operations.

The removed inactive installation was `0ac79dba-999c-4afe-8849-192f7e9e79bc`, uninstalled through operation `eafcfe7f-3b6b-4eec-b1ee-1e7a917199a5`. Its fresh preview had zero active runs, no model-cleanup nodes and Spark 2 explicitly retaining the shared model. The current installation and serving run stayed healthy. The UI's “21.9 GiB will be removed” headline described logical installation bytes despite the model-retention detail; the actual result removed zero model bytes and released a 74,387,433,571-byte reservation. Physical reclamation and reservation release should be reported separately.

## Controller defects and applied fixes

Signed patch source is [4d9e967f](https://github.com/kelchm/vonk-forge/commit/4d9e967fd67eaa7a73584d4fa2c46f384e26ea64), based on the exact published source. The same changes are forward-ported onto the fork's main in [draft PR #1](https://github.com/kelchm/vonk-forge/pull/1). Only API and worker images changed; there is no database/schema migration or agent upgrade.

| Finding | Correction and evidence |
| --- | --- |
| Library discarded part of a complete API page | Its 40-model window retained 42 hydrated recipes from 73 models/85 local recipes; 42 public actions remained stuck on Syncing and the custom Qwen recipe disappeared from search. The bounded window now retains a complete 100-row page, and known imported rows outside it can open exact details. Actual postdeployment UI showed all 86 then-current local recipes actionable. |
| Fleet compared unlike byte counts | Installed artifact bytes were compared with staging/cache/image reservations. Completeness now follows successful exact-rank installation state. Actual Fleet warnings cleared without receipt changes. |
| Public builds rejected valid egress capability | A static job-claim capability list was incorrectly used for a host-probed feature. The controller now checks the existing fresh inventory evidence; absent and stale evidence still fail. The real FLUX build then passed this gate. |
| Slow initial route publication became permanently failed | Acknowledgement now allows the supervisor's 120-second startup budget while remaining bounded by model evidence expiry. Delayed retries use normal authority checks; stale evidence waits for refresh and stopped runs do not retry. The real replacement Qwen run published automatically about 50s after runtime readiness. |
| Normal stop activated an empty route but returned 500 | The API reused its 30-second model-evidence freshness as the empty-route maintenance lease. Real inference became 503 while the API still reported running/published. Normal publication recovered the service; an independent 120-second empty-route lease then allowed the real 54-second withdrawal to finish. Model evidence freshness was not relaxed. |

The source lanes passed 287 controller tests with six existing skips, 47 Library-related frontend tests and production typecheck/build. The final withdrawal change separately passed 161 related tests with six existing skips; its forward-port passed 57 focused route tests. Regressions include missing ranks, absent/stale egress evidence, a complete and paginated Library, 45-second delayed acknowledgement, expiry, stale-to-fresh recovery and stopped-run rejection. These are code-level evidence, supplemented by the physical tests above.

Two remaining limitations matter for packing and recovery. Run admission subtracts full active reservations from current measured free memory, so already resident workloads can effectively be counted twice; this can reject small colocated workloads even with substantial free RAM. Route acknowledgement holds the publication lock and blocks the same worker's housekeeping while waiting; retries have a minimum 30-second delay, and generation files remain append-only as in stock renewal. Neither behavior was broadly redesigned during this pass.

The long install also exposed misleading Library recommendations: the unavailable old model still said no lifecycle change was required, and an installing placement was described as already installed. Signed candidate [0042a59e](https://github.com/kelchm/vonk-forge/commit/0042a59edb2981e7b311a8fb6f24c603305dc8c7) corrects both and is included in draft PR #1, but is not deployed yet. It requires matching, complete, healthy Fleet ranks and a published route before saying “Model is serving”; missing or degraded evidence calls for checking Fleet. Artifact-job sessions remain neutral because they do not publish inference routes. Installation labels distinguish completed, installing and mixed states. Forty-three focused tests and a production TypeScript/Vite build passed; the current-main forward-port has an identical web tree. Combined signed controller candidate `ba27bde2` adds the reviewed transition dependency from PR #4, passed five integration cases and is locally archived with rollback prepared. Deployment waits for a quiet operation boundary.

Existing browser URLs also retained an old HTML entry point after deployment, restoring the old 40-model window in that tab. A unique-URL navigation and direct uncached HTTP both returned the correct new asset, 73 models and all 86 then-current local recipe actions; the custom Qwen recipe and public Qwen recipes were searchable. The observed HTML response supplied ETag and Last-Modified but no explicit Cache-Control. Treat this as a stale HTML cache limitation rather than a failed image deployment, and refresh the HTML shell when verifying an upgrade. The corrected Library still retains bounded local history; imported catalog rows outside it can open exact details, while custom recipes outside the retained window require paging or a known direct URL.

The new native upload reproduced the slow path with warm source files: the sampled agent averaged about 36% of one CPU and 6,919 read syscalls/s, with no physical source-disk reads. The controller API averaged about one full CPU core, Caddy about 40% of a core, and measured I/O/memory pressure stayed low. Tiny isolated proxy tests and two short inference probes ran on the other Spark during parts of this interval; no competing bulk transfer ran. These observations support investigating per-chunk scheduling and processing rather than attributing the gap to raw disk throughput.

The proposed 1-MiB controller write aggregation improved a local body-only microbenchmark but was slower in direct network tests and showed only a small within-variance change behind Caddy (approximately 132→141 MB/s). It was excluded from deployment. The later native-profile sender used the exact two-worker Tokio runtime, release settings, Linux transport versions/features and real asynchronous file reads; all 16 final requests passed byte count, SHA256, flush and fsync verification. Larger reads improved the isolated TLS path by 22.4%, but that does not demonstrate a native-operation gain. An earlier 20-worker control is retained separately and excluded from these native-profile figures.

Two pass-through `BaseHTTPMiddleware` boundaries reduced the follow-up fixture's throughput by approximately 28–30%; all twelve transfers passed full verification. That measurable cost still does not explain the native 27.65 MB/s result. Production's request limits, trusted agent identity, bounded JSON parsing, security headers and metrics must remain intact. Read-only runtime inspection found no CPU quotas or throttling on the agent, API or Caddy, no restrictive CPU affinity, and no event-loop/debug tuning that explained the gap. Concrete remaining differences include the full authenticated application, native mTLS and service context, Docker bridge versus host networking, runtime image/AnyIO patch version and transfer duration. No transfer optimization or middleware rewrite has been deployed. All diagnostic listeners, unique containers, payloads, disposable private keys and owned samplers were cleaned; serving inference remained healthy.

A native-edge interruption in the earlier pass also caused the agent heartbeat task to exit on one transport error, despite successful local image import. The separate [signed heartbeat proposal](https://github.com/kelchm/vonk-forge/pull/2) retries only transient errors within the last confirmed lease and passed all 69 Rust agent library tests on Linux. It is not deployed: physical agents retain the officially signed package and its trust configuration.

## Recipes and current experiments

See the [recipe research and pins](recipes/README.md) for the genuine X search scope, direct dated posts, primary-source verification, licenses and exact initial profiles. Mia Qwen3.8 Flash Next dual is the fresh first-pass distributed candidate; FLUX.2 Klein NVFP4/ComfyUI is the complementary image job. GLM-5.3 EXL3/DFlash2 is a prepared fallback. Structural validation is complete; hardware acceptance is in progress. A separately reviewed offline FLUX variant now uses an immutable community ARM64 ComfyUI image, preserving the original failed public-build candidate.

FLUX's corrected source fixes missing executable dispatch and the distinction between a directory-mounted HTTP artifact and the model file inside it. Its first real native build passed controller admission and base-image import, then failed starting the installed egress proxy before Dockerfile execution. The first differential reproduced a missing `/dev/net/tun` inside the agent's private device namespace; moving only the proxy run command into a clean user service did not help because it reused existing rootless state. A subsequent isolated test reproduced the old Podman `/var/lib` networking issue described in [upstream issue 22227](https://github.com/podman-container-tools/podman/issues/22227). A clean user-manager lifecycle, coherent private runtime paths and a temporary empty CNI directory allowed the proxy container to start; its readiness probe then failed. Source inspection identified a probe that assumes one TCP read contains a status line. All diagnostic objects/helper processes were cleaned, the temporary directory was removed, and native binaries, service hardening and the serving Qwen stayed unchanged. No complete public-build workaround has been applied.

The separate [signed probe fix](https://github.com/kelchm/vonk-forge/pull/3) accepts fragmented status lines within a 256-byte cap and a fixed I/O deadline. Seven crate tests and five independent boundary/socket fixtures pass on macOS and in an official Rust 1.97.1 Linux/ARM64 container. The latter used no network, one CPU and 1 GiB, completed in 1.49s, and left no diagnostic container or source directory. This is source and socket-level validation; the installed helper is unchanged, and the broader clean-Podman lifecycle problem remains separate.

The dual Qwen image completed its normal offline build, upload and distribution/import on both Sparks. Base import took 112.04s; Dockerfile execution/commit took 286.7s; export took approximately 45s. The final 20,837,629,952-byte archive passed controller verification. Read-only image inspection confirmed the exact Mia patch receipt against the changed files, ARM64, UID 10001 and runtime label. Installed metadata is PyTorch 2.13.0+cu130 (CUDA 13.0) and vLLM `0.1.dev20073+g8e685d198`; these are image fingerprints, not a claim of stable-release qualification. Normal model installation succeeded on both nodes, and each native 25-file manifest matches the primary HF/Git SHA256 values. Two-GPU execution remains pending.

The normal Qwen model download is 132,734,506,208 bytes per node, about 265.47 GB aggregate. The largest individual file is 53.718 GB and has a one-hour native URL deadline; the repository has no one-hour aggregate limit. Transfer rates varied substantially. A simultaneous 45-second check found CPU busy below 0.5%, curl below 6% of one core, NVMe busy below 0.7%, negligible memory/I/O pressure and no swap or interface errors. Network receive rates tracked curl writes, supporting a remote/network wait rather than local resource saturation; this does not distinguish Hugging Face pacing from congestion. The largest-file transfers completed at approximately 40.75 and 44.93 MB/s over 21m55s and 19m55s. All bytes arrived by 13:22:41 on Spark 1 and 13:29:01 on Spark 2, about 54 and 60 minutes after acquisition began. Native final hashing followed; Spark 1 took approximately 118s. Both installations then passed all primary manifest hashes. Download-byte totals exclude the small generated local manifest counted in native installed-byte receipts.

The separate offline FLUX construction candidate uses `ghcr.io/aeon-7/comfyui-aeon-spark@sha256:7fda74d7af1d86455bfa58df5d36e761964017c7bce6f5d2f3564ba0b2deee3a`, ComfyUI 0.20.1 and PyTorch 2.9.1+cu130.
