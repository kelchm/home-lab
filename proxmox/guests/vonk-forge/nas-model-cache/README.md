# Vonk model cache on Athena

Dedicated share `vonk-forge-models-pve-sbx` follows `<workload-purpose>-<consumer-cluster>`. Its root is the managed model cache, without another nested directory. Controller API and worker mount it at `/state/model-cache`. PostgreSQL, secrets, other Controller state, image archives and build caches stay local. Sparks continue to serve from local storage, including PLE/runtime caches.

`create-share.py` previews by default and applies only with `--apply`, as root on Athena. It refuses an existing path/share/export, records the previous exports, creates an unbrowsable share, and restricts NFSv4.1 access to Controller VM `10.32.21.101`. The new share uses numeric UID/GID `10001:10001` and POSIX0750 to match Vonk's fixed runtime identity; no DSM login account is created. Root is squashed to guest, reserved client ports are required, and server writes are synchronous. No existing share, ACL or global NFS setting is changed. A partial failure is left for inspection rather than deleting potentially useful data.

Use `compose.nas-model-cache.yaml` as a fourth overlay alongside the deployed `docker-compose.yaml`, `compose.local.yaml`, and `compose.evaluation.yaml`. After `check-volume.py` verifies the named volume options, Docker's local NFS volume driver must mount the exact export before a container can start; it cannot fall back to an unmounted host directory. `nocopy` prevents Docker from populating the share from container contents. Hard mounts prioritize data integrity: a NAS outage can block cache I/O and Controller operations. Do not force-unmount an active cache. The original local cache remains mounted underneath `/state` and must be preserved until acceptance and rollback review complete.

Run `check-volume.py` before every cutover and after volume qualification. It rejects an existing same-named plain local volume or any changed driver options. Never allow Compose to reuse an unverified volume. Before cutover, test this exact volume with disposable containers using the deployed Controller image and UID10001: file creation, fsync, atomic replacement, cross-process locks, hash verification and denial for a different UID. Test an unavailable export separately and confirm no local fallback. Verify the resolved Compose changes only the two model-cache mounts and adds the NFS volume.

Quiesce Controller API/worker cache writers, back up the local database, and copy the current model-cache directory into the share while preserving the five child directories. All copy/import/hash processes using NFS must run as UID/GID10001 (for example, a disposable container mounting the old cache read-only and the NAS volume read-write). Squashed root cannot access the share. Create directories0750 and regular files0640 as that user; do not preserve foreign ownership or copy HF symlinks as symlinks. Verify every expected object hash and size. Keep the existing database and identity/trust history. Copy retained Spark/HF files only through an exact canonical-hash import plan, as regular files staged and atomically published; no fabricated database receipts or legacy runtime compatibility. Normal cache preview/download must recognize those bytes and fetch only missing approved files.

Rollback: quiesce API/worker, preserve any new NAS objects/partial checkpoints, and restore the previous three-file Compose configuration with the exact prior images and original local state volume. Restart through Compose. Do not restore an old database or rewind trust; the same DB can reconcile missing newly cached NAS-only objects, so avoid requesting those until verified import back to local storage or reapplying the NAS mount. Never use `docker compose down -v`, prune retained volumes, or delete the NAS share as part of routine rollback.

Physical acceptance and exact receipts must be recorded before marking the migration complete. NAS snapshots/backup policy are separate from the retained original cache and are not implicitly configured by this overlay.
